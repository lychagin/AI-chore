# Ночной стек локально

Нужен **только** для инфра-специфики: поведение файлового хранилища, порядок джоб,
содержимое образов, проверка бэкенд-фикса в «ночных» условиях. Для разбора обычных
падений коллекций достаточно локального dev-стенда — см. [local-repro.md](local-repro.md).

Команд здесь нет: они целиком состоят из имён джоб, портов и переменных конкретного
проекта. Есть чек-лист того, что должно быть, и грабли, на которые наступают все.

---

## Что нужно, чтобы поднять ночной стек локально

**1. Скрипт подъёма, принимающий фазу аргументом.**
Ночной пайплайн поднимает стек не одной командой, а тремя шагами, между которыми
выполняется загрузка данных. Локально нужен тот же скрипт с той же разбивкой — иначе
воспроизводится не ночной стек, а обычный docker-compose.

```
фаза infra   → инфраструктура: база, брокер, кэш, хранилище файлов
загрузка данных
фаза app     → сервисы приложения
```

**2. Переменные, которые в CI приходят сами.**
Скрипт написан под CI и читает переменные окружения раннера: каталог проекта,
идентификатор пайплайна, короткий SHA коммита, номер джобы. Локально их надо задать
руками — иначе скрипт либо падает, либо собирает контейнеры с пустыми именами.

Отдельно задаётся **имя compose-проекта**: от него зависят имена контейнеров и сети.
Если не задать, локальный стек столкнётся с обычным dev-стеком.

**3. Память.**
Полный стек — это вся инфраструктура плюс все сервисы приложения. На исходном проекте
это ~9 ГБ под контейнеры. На WSL2 потолок задаётся в `.wslconfig` и применяется только
после полной перезагрузки подсистемы, а не после перезапуска Docker.

**4. Окружение для коллекций.**
Адреса и учётные данные в файле окружения для docker-стека отличаются от dev: другие
порты, другой хост API. Прогон ночным окружением против dev-стенда даёт connection
refused, который легко принять за падение сервиса.

---

## Грабли

**Адреса сервисов внутри сети и снаружи — разные.**
Часть компонентов в ночном стеке намеренно не проброшена на хост. Скрипт загрузки
данных, запускаемый **с хоста**, до них не достучится: в логе будет
`ECONNREFUSED 127.0.0.1:<порт>`, кэш не заработает, а загрузка пройдёт медленно и молча.
Такие адреса передаются явно — внутренним IP контейнера, а не `localhost`.

**Порядок «сервисы → данные» ломает прогон.**
Это та самая первая внешняя причина из Фазы 0. Локально она воспроизводится тривиально
и стоит того, чтобы проверить один раз: поднять сервисы, затем перезагрузить данные и
посмотреть, что коллекции начнут получать 404 на объекты, которые в базе есть.

**Базовые образы не пересобираются, если уже существуют.**
Проверяя фикс, легко поднять стек на образе, собранном вчера из другой ветки.
Признак — джоба сборки отработала за секунды. Пересборка форсируется явно.

**Пересборка образа ради одной правки — дорого.**
Для проверки бэкенд-фикса быстрее подложить собранные артефакты в уже поднятый
контейнер (`docker cp` в каталог сборки + рестарт сервиса), чем гонять полный цикл
сборки образов. Базовую линию для сравнения снимают из образа до подмены.

**`nohup ... &` внутри фоновой задачи молча убивает длинную команду.**
Если подъём запускается из агентской сессии в фоне, длинные шаги надо запускать так,
чтобы процесс пережил завершение вызова инструмента — иначе фаза обрывается на середине
без сообщения об ошибке.

## Когда стек не нужен

Большинство разборов закрывается без него:

| Задача | Нужен ночной стек? |
| --- | --- |
| Понять, почему коллекция получила 422 | Нет — хватит артефактов |
| Воспроизвести падение валидации | Нет — локальный dev-стенд и тот же раннер |
| Проверить бэкенд-фикс | Обычно нет — подмена артефактов в контейнере |
| Разобрать 504 под нагрузкой | Да, и даже он воспроизводит не всегда |
| Проверить поведение файлового хранилища | Да |
| Воспроизвести порядок джоб | Да |

Если ответ «нет» — не поднимай. Полный стек стоит времени и памяти, а даёт ту же
картину, что и dev-стенд, во всех случаях кроме двух нижних строк.
