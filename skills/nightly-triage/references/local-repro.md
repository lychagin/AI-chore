# Локальное воспроизведение ночного падения

Разница «ночь vs локально» — в **раннере**, а не в стеке. Ночная джоба гоняет коллекции
одним раннером, в фиксированном порядке, из корня репозитория, с предварительной
генерацией фикстур. Ручной запуск одной коллекции этого не воспроизводит и даёт ложные
причины.

## Правильный запуск

```bash
node tests/run-collections.js \
  --env tests/environment/local-dev.json \
  --filter <substring> \
  --log-formats json \
  --retries 0
```

Что это даёт по сравнению с ручным запуском одной коллекции:

- **предварительная генерация фикстур** — генерируемые файлы создаются автоматически;
- **рабочий каталог = корень репозитория** — иначе ломаются поля формы со ссылкой
  на файл;
- **ночной порядок и общий набор** — без этого не видно межколлекционного загрязнения.

Полезные флаги: `--env`, `--filter` / `--include-regexp` / `--exclude-regexp`,
`--concurrency`, `--retries`, `--log-formats`, `--summary-formats`, `--bail`,
`--skip-fixtures`.

Окружения: одно для host-процессов (`npm run dev`), другое для docker-стека — ночь
использует второе.

## Что воспроизводится локально, а что нет

| Класс падения | Воспроизводится локальным раннером? |
| --- | --- |
| Валидация и контракт (400/422/403) и каскад | Да, обычно с первого прогона |
| Недетерминированный порядок данных из базы | Да, но не каждый раз — гонять несколько раз |
| Межколлекционное загрязнение состояния | Да, но нужен полный набор в ночном порядке, а не одна коллекция |
| Деградация под нагрузкой (504/503 к концу прогона) | **Нет.** Локальная машина слабее CI-раннера; локальный таймаут при нехватке памяти — не то же самое |
| Инфра-специфика (ссылки файлового хранилища) | Нет, нужен полный docker-стек |
| Порядок «данные загружены после старта сервисов» | Только вручную: поднять бэкенд, затем прогнать миграцию и загрузку данных при работающих сервисах |

Последняя строка — единственный способ воспроизвести самую частую внешнюю причину.
Ловится она за минуту, а без воспроизведения обсуждается часами.

## Генерируемые фикстуры

Крупные бинарные фикстуры в репозитории обычно не хранят, а генерируют скриптом. Без
них коллекции падают «мимо кассы»: тест на загрузку большого файла получает `no such
file`, а тест на превышение размера — не тот код ответа.

Раннер генерирует их сам. При ручном запуске одной коллекции — генерировать вручную;
список должен быть описан в манифесте фикстур проекта.

## Ловушки повторных прогонов

- **Часть коллекций нельзя перепрогонять на уже отработанной базе.** Типичный механизм:
  коллекция при повторе тянет переход состояния сущности, упирается в условное правило,
  которое резолвится в несуществующий объект, и получает fail-closed 403 с каскадом 404.
  Лечится перезагрузкой данных и рестартом стенда перед прогоном, а не правкой коллекции.
- **Отключённые коллекции (`*.disabled.json`) раннер пропускает встроенно.**
  Самодельные скрипты, берущие коллекции по маске `*.json`, подхватывают намеренно
  отключённые файлы — маску надо фильтровать.
- **Свежие данные меняют результат.** «Одна коллекция на свежих данных проходит»
  не опровергает ночное падение: ночью она стартует после сотни других коллекций.

## Unit-тесты

Ночные unit-тесты гоняются на хосте из checkout ветки, docker-стек им не нужен —
поэтому они не ловят расхождения, вызванные содержимым образов. Если ночь красная
на unit-тестах, а локально зелено, дело почти наверняка не в коде, а в окружении джобы.

Локальная гочча, которая стоит проверки, если `npm test` из корня падает массово
(`duplicate manual mock`, `Test suite failed to run`): в репозитории может лежать git
worktree внутри отслеживаемого каталога, и раннер видит один и тот же файл дважды.
Обход — добавить путь worktree в `--modulePathIgnorePatterns`.
