# Bugfix

Оркестратор полного цикла: тикет → причина → фикс → живая проверка → MR.

Не дублирует существующие скиллы, а вызывает их на своих фазах:
`/read-bug` → **этот скилл** → `/pre-mr` → `/mr` → `/resolve-remarks`.

> Конкретика — [проект-пример OrderShop](../../examples/example-project.md).
> Список подстановок — в конце файла.

## Использование

```
/bugfix 1042            # обычный запуск, среду определяем по ходу
/bugfix 1042 --stand    # сразу форсировать проверку на общем стенде
/bugfix 1042 --local    # сразу форсировать локальную проверку
/bugfix 1042 --no-stand # анализ по коду + unit-тесты, без стенда
```

---

## Фаза 1: Прочитать тикет

Вызвать `/read-bug <ID>` — описание, скриншоты, комментарии, связанные баги.

Из результата зафиксировать **три вещи** и вывести их пользователю:

1. **Что видит пользователь** — наблюдаемый симптом, без интерпретации.
2. **Заявленная в тикете причина** — если она вообще названа.
3. **Ожидаемое поведение** — как должно быть.

Если хотя бы одно непонятно — задать точечные вопросы и **не идти дальше**. Угадывать
постановку дороже, чем спросить.

---

## Фаза 2: Классификация по коду [до любого запуска]

Это самая ценная фаза. Часто она же и последняя перед фиксом — стенд не понадобится.

Найти в коде путь от симптома к причине. Определить **слой**:

| Слой | Признак |
| --- | --- |
| `FRONTEND` | Данные в API есть, на экране нет или не те |
| `DTO_MAPPER` | Поле есть в сущности, но вырезается маппером ответа |
| `PROJECTION` | Связанное поле пустое в API, хотя в базе заполнено |
| `DATA_MODEL` | Поля или связи нет в модели — нужны миграция и загрузка данных |
| `CONTRACT` | Спецификация не описывает поле → его нет в сгенерированном валидаторе |
| `PERMISSIONS` | 403 или пустая выдача при существующих данных |
| `SEED_DATA` | Локально или на стенде нет нужной сущности, код корректен |
| `NOT_A_BUG` | Поведение соответствует требованиям, либо это лаг деплоя |

**Заявленную в тикете причину проверять, а не принимать.** Два реальных прецедента
с исходного проекта: в одном случае настоящей причиной оказалось невыданное право,
а не то, что было написано в тикете; в другом фикс вообще не требовался — наблюдался
лаг деплоя, и на актуальной версии баг не воспроизводился.

Вывести пользователю: слой, конкретные `file:line`, механизм — «что именно, в какой
строке и при каком условии даёт наблюдаемый эффект».

Если по коду картина **не сходится** — переходим к Фазе 3 за живыми данными.
Если сходится и слой очевиден (`FRONTEND`, `DTO_MAPPER`, `PROJECTION` с однозначным
местом) — стенд может не понадобиться, см. Фазу 3, вариант «без стенда».

## Фаза 3: Выбор среды проверки [развилка]

Ответить на три вопроса. **Если хоть на один ответ «не знаю» — спросить пользователя**
через `AskUserQuestion`, не решать молча.

1. **Нужны ли живые данные, которых локально нет?**
   Баг про конкретную запись, про историю событий, про данные конкретной организации,
   про то, что «было создано давно» → **общий стенд**.

2. **Воспроизводится ли на свежих тестовых данных?**
   Баг про общий сценарий, доступный на сидовых данных → **локально**.

3. **Достаточно ли чтения кода и unit-теста?**
   Однозначное место в коде + фикс покрывается unit-тестом → **без стенда**.

Формулировка вопроса пользователю (опции самодостаточны):

> Где проверяем баг <ID>?
>
> - **Локально** — воспроизводится на тестовых данных, используем локальный бэкенд
> - **На общем стенде** — нужны реальные данные, которых в локальных нет
> - **Без стенда** — причина однозначна по коду, достаточно unit-теста

### 3a. Ветка «локально»

**Сначала проверить, поднят ли бэкенд. Не поднимать молча.**

```bash
.scripts/dev-daemon.sh status
curl -s -o /dev/null -w '%{http_code}' --max-time 5 http://localhost:3000/ || echo "недоступен"
```

Если не поднят — **спросить**, а не запускать:

> Локальный бэкенд не запущен. Что делаем?
>
> - **Поднять локально** — займёт несколько минут
> - **Сходить на общий стенд** — он уже работает, данные реальные
> - **Обойтись без стенда** — ограничиться unit-тестом и анализом кода

Если пользователь выбрал поднять — запускать в фоне и **не опрашивать** счётчик:
поллинг длинной операции съедает контекст на строках прогресса.

### 3b. Ветка «общий стенд»

**Отдельно и обязательно спросить про запись данных:**

> Можно ли менять данные на стенде при проверке бага <ID>?
>
> - **Только чтение** — запросы к базе, GET через API, логи контейнеров (по умолчанию)
> - **Можно создавать и править** — потребуется создать тестовую сущность

**По умолчанию — read-only.** Запись только после явного «да». Если запись разрешена —
записать в отчёт, что именно было создано или изменено, чтобы это можно было убрать.

Общий стенд — это чужие данные и чужая работа. Созданная и забытая тестовая сущность
всплывёт через месяц в чьём-то отчёте.

Read-only инструменты стенда — прямой запрос к базе и чтение логов сервисов; конкретные
команды зависят от того, как организован доступ (см. «Точки подстановки»).

### 3c. Ветка «без стенда»

Допустима, но в итоговом отчёте **явно написать**: «живой прогон не выполнялся, потому
что <причина>». Умолчать нельзя: молчание читается как «проверено».

## Фаза 4: Изоляция

```bash
git ls-remote --exit-code origin HEAD >/dev/null 2>&1 && echo "remote OK" || echo "NO REMOTE"
```

Создать worktree, не переключая активную ветку основного чекаута:

```bash
git worktree add .claude/worktrees/task-<ID> -b fix/TASK-<ID>-<slug> origin/<BASE_BRANCH>
```

⚠️ **Зависимости в worktree.** `npm ci` в новом worktree — это минуты и гигабайты.
Быстрее разложить симлинки на `node_modules` основного чекаута. Но если worktree лежит
внутри дерева репозитория, резолвер модулей может подняться вверх и подхватить артефакты
основного чекаута сам — тогда тесты будут проверять не тот код. Проверь это один раз
на своём проекте и запиши вывод: цена ошибки — час на ложный результат.

## Фаза 5: TDD

1. **Падающий тест первым.** Тест должен падать по той же причине, что и баг, — сверить
   сообщение об ошибке с наблюдаемым симптомом. Тест, падающий по другой причине,
   позеленеет от любого изменения.
2. Фикс — **на правильном слое** из Фазы 2. Обосновать выбор слоя явно: правка во
   фронтенде того, что должно чиниться в проекции, вернётся тем же багом на другом экране.
3. Тест зеленеет.
4. Проверить **соседние места того же класса**: другой маппер, другой экран, другой
   обработчик. Полуприменённый фикс — самая частая находка на ревью.

```bash
npm test -- --testPathPattern="<файл>"
npm run lint
```

> После изменения спецификации API — пересборка до тестов: она пересоздаёт генерируемые
> валидаторы, и без неё тест проверяет предыдущий контракт.

---

## Фаза 6: Живая верификация

Обязательна для бэкенд- и фронтенд-слоёв. Пропуск только для варианта «без стенда»
из Фазы 3в — с явной записью причины.

- **Локально:** перезапустить бэкенд, выполнить запрос.
- **Ночной стек:** подложить собранные артефакты в контейнер вместо пересборки образов —
  это минуты вместо часа.
- **Общий стенд:** проверка в рамках выданного разрешения на запись.

Зафиксировать **до** и **после**: что возвращал API или показывал экран до фикса и после.
Без сравнения «до/после» верификация не считается выполненной — «теперь работает» без
зафиксированного «раньше не работало» не отличается от «я не проверял».

## Фаза 7: Коммит и MR

1. Коммит по формату проекта:

   ```
   fix(<scope>): [TASK-<ID>] <subject на английском, ≤72 символов>
   ```

   Тело — можно на русском. Если CI проверяет формат сообщения, сверься с его
   правилами: ссылки вида `#N` в теле некоторые линтеры принимают только с начала
   абзаца и иначе ругаются на футер — сообщение об ошибке при этом вводит в заблуждение.

2. Прогнать **`/pre-mr`** — враждебное ревью, мутационная проверка тестов, скан
   секретов. Не создавать MR, пока остаются находки Critical.
3. `git branch -f <BASE_BRANCH> origin/<BASE_BRANCH>` → rebase → push.
4. MR через `/mr`. **MR title обязан быть валидным commit subject** — при squash он
   станет финальным коммитом и провалит валидацию, если формат нарушен.
5. Ремарки ревьюеров — через `/resolve-remarks`.

## Фаза 8: Отчёт

```markdown
## Баг <ID>: <заголовок>

**Слой:** <из таблицы Фазы 2>
**Заявленная в тикете причина:** <подтверждена / опровергнута: чем>
**Реальная причина:** <механизм, file:line>

### Изменённые файлы

- `<путь>` — <что>

### Тесты

- <новый тест> — падал до фикса: да/нет
- Прогон: `<команда>` → <результат>

### Живая верификация

- Где: <локально / общий стенд / не выполнялась, потому что …>
- До: <что возвращало>
- После: <что возвращает>

### MR

<ссылка>

### Кратко для тикета

<3 предложения без жаргона и имён кода>
```

Блок «Кратко для тикета» — ровно три предложения, без имён файлов, функций и полей,
чтобы тестировщик или менеджер вставил их в трекер как есть.

## Точки подстановки

| Что | Сейчас (OrderShop) | Чем заменить |
| --- | --- | --- |
| Таблица слоёв | 8 слоёв | Своими; убрать те, которых у тебя нет |
| `--stand` | общий тестовый стенд | Своим стендом; команды доступа к нему — свои |
| `.scripts/dev-daemon.sh` | скрипт-демон | Штатным способом запуска стенда |
| `<BASE_BRANCH>` | `main` | Своей целевой веткой |
| Формат коммита | `fix(scope): [TASK-ID] subject` | Своим |
| `.claude/worktrees/` | каталог worktree | Своим расположением |

**Таблица слоёв — главное, что стоит настроить.** Она отвечает на вопрос «где чинить»,
и её ценность целиком в том, насколько точно она описывает твою архитектуру. Слои
`PROJECTION` и `DATA_MODEL` осмысленны там, где есть отдельный слой описания модели;
если у тебя обычный ORM — они схлопываются в один. Заполняй по мере разбора реальных
багов, а не заранее.

## Заметки

- Анализ и отчёты — на русском, код и команды — на английском.
- Скилл **не устанавливает** новые сервисы и не меняет порты.
- Инфра-проблемы: максимум 2 попытки → спросить пользователя.
- Связанные скиллы: [`/read-bug`](../read-bug/SKILL.md), [`/pre-mr`](../pre-mr/SKILL.md),
  [`/mr`](../../commands/mr.md), [`/resolve-remarks`](../resolve-remarks/SKILL.md),
