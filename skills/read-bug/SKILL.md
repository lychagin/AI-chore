# Read Bug

Читает задачу или баг из трекера OpenProject по ID: описание + вложенные скриншоты +
комментарии коллег из вкладки Activity. Затем собирает контекст и формулирует
вероятную причину. Если данных не хватает — сообщает об этом и задаёт точечные вопросы.

## Использование

```
/read-bug <id>
```

Например: `/read-bug 1042`

---

## Доступ к OpenProject

**Основной путь — MCP-сервер `openproject`** (`mcp__openproject__*`). Он сам подхватывает
`OPENPROJECT_URL`, `OPENPROJECTTOKEN` и CA из `.envrc`, отдаёт компактный текст вместо
сырого JSON и при обрыве связи возвращает внятную ошибку.

**Fallback — `curl`**, если инструментов `mcp__openproject__*` в сессии нет (сервер не
поднят, headless-прогон). Тогда переменные подгружаются инлайн — direnv до Bash-tool
не доходит:

```bash
source .envrc 2>/dev/null
# авторизация -u "apikey:${OPENPROJECTTOKEN}", TLS --cacert "$NODE_EXTRA_CA_CERTS",
# таймаут --max-time 30 (без --cacert curl молча вернёт пусто)
```

## Фаза 1: Прочитать описание бага

### Шаг 1: Получить work package

```
mcp__openproject__get_work_package(id: <id>)
```

Возвращает: тип, статус, приоритет, автора, исполнителя, даты, `lockVersion` и описание
(при длинном описании — путь к файлу с полным текстом).

Fallback:

```bash
source .envrc 2>/dev/null
mkdir -p tmp/<id>
curl -s --max-time 30 --cacert "$NODE_EXTRA_CA_CERTS" -u "apikey:${OPENPROJECTTOKEN}" \
  "${OPENPROJECT_URL}/api/v3/work_packages/<id>" -o tmp/<id>/wp.json
```

Из JSON нужны: `subject`, `_links.type.title`, `_links.status.title`,
`_links.assignee.title`, `_links.priority.title`, `description.raw`.

Если тикет не найден или нет доступа — сообщить пользователю и прекратить.

### Шаг 2: Извлечь текст и ссылки на скриншоты

В описании встречаются HTML-сущности (`&quot;` → `"`, `&nbsp;` → пробел) — нормализовать,
и встроенные скриншоты `<img ... src="/api/v3/attachments/<attId>/content">`.

### Шаг 3: Скачать и проанализировать скриншоты

```
mcp__openproject__get_work_package_attachments(id: <id>, download: true)
```

Скачивает все вложения (включая не-inline) и возвращает пути. Каталог по умолчанию —
`/tmp/mcp-openproject-wp-<id>`; свой путь задаётся `target_dir`, например `tmp/<id>`.

Fallback:

```bash
source .envrc 2>/dev/null
curl -s --max-time 30 --cacert "$NODE_EXTRA_CA_CERTS" -u "apikey:${OPENPROJECTTOKEN}" \
  "${OPENPROJECT_URL}/api/v3/work_packages/<id>/attachments" -o tmp/<id>/attachments.json
# затем для каждого id из _embedded.elements[]:
curl -sL --max-time 30 --cacert "$NODE_EXTRA_CA_CERTS" -u "apikey:${OPENPROJECTTOKEN}" \
  "${OPENPROJECT_URL}/api/v3/attachments/<attId>/content" -o tmp/<id>/att-<attId>.png
```

Каждый файл прочитать инструментом Read (он отображает изображения) и проанализировать:
что на скриншоте, какие значения/ошибки видны, как связано с описанием.

> Расширение не критично — Read определит тип; при сомнениях `file -b <путь>`.

## Фаза 2: Прочитать Activity (комментарии)

### Шаг 4: Получить активности

```
mcp__openproject__get_work_package_activities(id: <id>)
```

Возвращает комментарии с автором и датой (имена пользователей резолвятся сервером);
`include_changes: true` добавляет историю изменений полей — она нужна, когда важно,
когда и кем менялся статус.

Fallback:

```bash
source .envrc 2>/dev/null
curl -s --max-time 30 --cacert "$NODE_EXTRA_CA_CERTS" -u "apikey:${OPENPROJECTTOKEN}" \
  "${OPENPROJECT_URL}/api/v3/work_packages/<id>/activities" -o tmp/<id>/activities.json
```

Из `_embedded.elements[]` взять записи с непустым `comment.raw`: дата — `createdAt`,
автор — по `_links.user.href` (в API v3 у него **нет** `title`). Имя запрашивается
отдельно, по одному разу на уникального пользователя:

```bash
source .envrc 2>/dev/null
curl -s --max-time 30 --cacert "$NODE_EXTRA_CA_CERTS" -u "apikey:${OPENPROJECTTOKEN}" \
  "${OPENPROJECT_URL}/api/v3/users/<userId>" | jq -r .name
```

Если запрос не прошёл — подписывать комментарий как `user/<userId>`, не бросать разбор.

**Отфильтровать машинный шум** (оставить только человеческие комментарии): записи об
автоматике обычно содержат маркеры — «Merge Request влит», «Задеплоено на staging»,
«pipeline …», либо это просто имя ветки одним токеном (`task_<id>_…`, `<slug>_<id>_…`,
часто с опечатками типа `tast_…` и подчёркиваниями). Такие в анализ не включать (но если
коллега явно что-то написал по сути бага — учитывать).

## Фаза 3: Собрать контекст и проанализировать

### Шаг 5: Синтез

Свести воедино: заголовок + тип/статус, суть описания, факты со скриншотов, выводы из
комментариев коллег. Сформулировать **вероятную причину** и затронутую область
(сервис/модуль/поле). Если уместно — предложить, где в коде искать (но без правок).

### Шаг 6: Если данных не хватает

Если по описанию/скриншотам/комментариям непонятно, в чём проблема или каков ожидаемый
результат — **не угадывать**. Чётко сообщить, чего не хватает, и задать 1–3 точечных
вопроса пользователю (через AskUserQuestion или текстом).

---

## Шаг 7: Вывод

Выдать структурированную сводку **на русском** (правило проекта):

```
🐞 <тип> <id> — <subject>
Статус: <status> | Приоритет: <priority>

## Описание
<суть текстом, нормализованный HTML>

## Скриншоты (N)
- att-<id>: <что видно, ключевые значения>

## Комментарии коллег (N)
- <автор>, <дата>: <суть>

## Вероятная причина
<анализ: что ломается и почему, затронутая область>

## Чего не хватает (если есть)
- <вопрос 1>
- <вопрос 2>
```

Ссылка на задачу: `${OPENPROJECT_URL}/work_packages/<id>`.

---

## Заметки

- Анализ, рассуждения и сводка — **на русском** (код/команды — английский).
- Скачанные артефакты складывать в `tmp/<id>/` (не коммитить).
- Это **read-only** навык: код не правим, задачу в трекере не меняем.
- Связанный навык: `/mr` (тоже ходит в OpenProject и знает про env).

## Точки подстановки

| Что | Сейчас | Чем заменить |
| --- | --- | --- |
| Трекер | OpenProject, REST API v3 | Своим — см. [README.md](README.md) |
| Фильтр машинного шума (шаг 4) | маркеры «Merge Request влит», «Задеплоено», имя ветки одним токеном | Маркерами своей автоматики |
| Каталог артефактов | `tmp/<id>/` | Своим временным каталогом |

**Фильтр шума стоит настроить в первую очередь.** В активной задаче половина записей —
следы CI и ботов. Без фильтра агент читает их наравне с комментариями коллег и делает
выводы из строки вида `task_1042_fix` — это не мнение, это имя ветки.
