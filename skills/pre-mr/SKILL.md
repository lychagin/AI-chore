# Pre-MR Gauntlet

Пропускает ветку через враждебное ревью **до** того, как её увидит человек.

Смысл: собственные правки защищаются собственными рассуждениями. Ревьюер, который видит
только diff и постановку, ловит то, что автор объяснил себе и потому перестал замечать.

## Использование

```
/pre-mr                 # против origin/develop
/pre-mr <target-branch> # против другой целевой ветки
```

---

## Фаза 0: Подготовка diff

```bash
git branch -f develop origin/develop      # локальный develop бывает stale
git fetch origin --quiet
git diff origin/develop...HEAD > tmp/pre-mr-diff.patch
git log --oneline origin/develop..HEAD
git diff --stat origin/develop...HEAD
```

Если diff пустой — сообщить и остановиться.

### Скан на секреты [до всего остального]

```bash
git diff origin/develop...HEAD | grep -inE 'token|secret|password|api[_-]?key|BEGIN [A-Z ]*PRIVATE KEY'
```

Любое совпадение разбирается вручную. Если секрет реально попал в коммит — **остановить
процесс**, сообщить пользователю: нужен перевыпуск ключа и переписывание истории ветки
(`git filter-branch --index-filter`, не `rebase -i` — он запрещён правилами проекта).

---

## Фаза 1: Враждебный ревьюер [субагент]

Запустить **одного** субагента с изолированным контекстом. Ему передаётся:

- содержимое `tmp/pre-mr-diff.patch`;
- текст постановки (описание бага/задачи);
- **ничего из твоих рассуждений** — ни объяснений причины, ни того, почему фикс такой.

Промпт субагенту:

> Ты враждебный ревьюер. Твоя задача — сломать это изменение, а не одобрить его.
> Даны только diff и постановка. Найди места, где изменение не делает того, что заявлено.
>
> Ищи прицельно:
>
> 1. **Проглоченные исключения** — `catch` без rethrow/лога; `beforeDelete`/хуки, где
>    выброшенная ошибка теряется вызывающим кодом.
> 2. **Полуприменённый фикс** — исправлена одна ветка кода из нескольких эквивалентных;
>    поправлен один миксин из двух; поле добавлено в один DTO-маппер, но не в соседний.
> 3. **Пустые guard'ы** — условие, которое never/always true; проверка на `null` там,
>    где значение не может быть `null`; ранний выход, до которого не доходит поток.
> 4. **Необработанные ошибки ввода-вывода и сети** — таймауты, отвалившееся соединение,
>    отсутствующий файл, пустой ответ API, принятый за валидный.
> 5. **Тесты, которые пройдут и без фикса** — ассерт на то, что работало и раньше;
>    мок, возвращающий ровно ожидаемое; проверка формы объекта вместо значения.
> 6. **Граничные случаи дат/времени** — `date-only` значения, попадающие в хранилище как
>    `00:00Z`; сравнение через `>=` vs `>`; таймзоны.
>
> Для каждой находки: файл и строка из diff, что именно сломается, при каких входных
> данных. Категория — Critical / Major / Minor.
> Critical = изменение не чинит заявленную проблему, ломает существующее поведение или
> теряет ошибку. Не выдумывай находки: если ветка чистая — так и скажи.

Субагент **не редактирует файлы** — только отчёт (правило «субагенты на разведку»).

## Фаза 2: Мутационная проверка новых тестов

Для каждого нового/изменённого теста в diff:

1. Найти строки продакшн-кода, которые он покрывает.
2. **Откатить их** (закомментировать фикс или инвертировать условие).
3. Прогнать тест фильтром: `npm test -- --testPathPattern="<файл>"`.
4. Тест **обязан упасть**. Не упал → тест ничего не проверяет, это находка Critical.
5. Вернуть код.

Проверять правкой рабочего дерева, не коммитом. После проверки — `git diff` должен
совпадать с исходным. Сверить обязательно.

Если тестов в diff нет вообще — это само по себе находка Major, кроме случаев чисто
документарных/конфигурационных изменений.

---

## Фаза 3: Живая верификация

Правило «Верификация до слова готово» (`.claude/critical-rules.md`) действует и здесь:
прохождения unit-тестов **недостаточно**.

- Бэкенд-фикс → прогон на пересобранном стенде (локальный docker, подмена собранных
  артефактов на ночном стеке, либо общий тестовый стенд) с фактическим запросом к API.
- Фронт-фикс → проверка в браузере на нужном стенде.
- Изменения только в документации/конфигах → живой прогон не нужен, отметить это явно.

Если живой прогон невозможен — записать в отчёт причину. Пустая графа недопустима.

---

## Фаза 4: Цикл до нуля Critical

1. Исправить все Critical.
2. **Перезапустить Фазу 1** на обновлённом diff — новый субагент, чистый контекст.
3. Повторять, пока Critical не станет ноль.
4. Major — исправить либо явно обосновать, почему оставляем.
5. Minor — записать, решение за пользователем.

Не переходить к MR, пока цикл не сошёлся.

## Заметки

- Скилл **не создаёт MR** — он только пропускает или не пропускает ветку. MR делает
  `/mr` или `/bugfix`.
- Отличие от `/review-bug`: тот проверяет чужой MR по багу с воспроизведением на стенде.
  Этот — свою ветку до публикации.
- Работает на любой ветке: багфикс, фича, рефакторинг, правки документации.
- Анализ и отчёт — на русском.
