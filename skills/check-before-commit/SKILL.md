# Проверка перед деливери

Прогоняет ветку через полный цикл на чистом окружении. Смысл — поймать то, что не
видно в рабочей сессии: расхождение сгенерированных артефактов с кодом, зависимость
от данных, оставшихся от предыдущих прогонов, и «зелёные» тесты, которые на самом деле
не пересобирались.

Каждый шаг выполняется последовательно. При ошибке — остановиться, разобраться,
исправить, продолжить с того же шага. Не пропускать.

> Команды ниже — под [проект-пример OrderShop](../../examples/example-project.md).
> Список подстановок — в конце файла.

---

## Шаги

### Чистое состояние данных

1. **Миграция с удалением схем:** `npm run db:migrate:reset`
2. **Загрузка тестовых данных:** `npm run db:seed`

Порядок важен: сид поверх старой схемы даёт ошибки, которые выглядят как баги кода.

### Сборка

3. **Сборка с нуля, без кеша:** `npm run build -- --force`

Флаг обязателен. Кеш сборки — самый частый источник «у меня работало»: тесты
резолвят собранные артефакты, и без пересборки проверяют предыдущую версию.

### Живой стенд

4. **Запуск backend в фоне:** `.scripts/dev-daemon.sh start`
5. **Ожидание запуска:** 30 секунд
6. **Проверка статуса:** `.scripts/dev-daemon.sh status` — убедиться, что поднялся

### Тесты

7. **Интеграционные тесты:** если для текущих изменений есть коллекция —

   ```bash
   node tests/run-collections.js -c tests/function/<имя коллекции>.json
   ```

   Имя определяется по ветке и содержимому изменений.

8. **Unit-тесты:** `npm test`
9. **Линт:** `npm run lint`

### Коммит и описание

10. **Проверка требований к коммиту** по:
    - `.claude/hooks/pre-commit.md` — чек-лист проверок
    - правилам формата сообщения коммита, принятым в проекте
11. **Создание коммита** по правилам из шага 10
12. **Ребейз на целевую ветку:** `git rebase <BASE_BRANCH>`
13. **Описание MR:**
    - Разобрать коммиты ветки: `git log <BASE_BRANCH>..HEAD --oneline`
    - Разобрать diff: `git diff <BASE_BRANCH>...HEAD --stat`
    - Сгенерировать описание в markdown
    - Сохранить в `.swap/mr-description/<branch-name>.md` (создать каталог, если нет)
    - Вывести содержимое **raw markdown в code block** для копирования

---

## Правила

- Все шаги должны пройти без ошибок.
- При ошибке — исследовать, исправить, затем продолжать workflow.
- Не пропускать шаги. Пропущенный шаг обесценивает остальные: смысл в том, что
  цепочка прошла целиком на чистом окружении.
- Описание MR всегда выводить как raw markdown в code block, а не рендеренный —
  иначе его нельзя скопировать без потери разметки.

---

## Чем отличается от `/pre-mr`

Соседний скилл [`pre-mr`](../pre-mr/SKILL.md) решает другую задачу: он ищет дефекты
в diff'е глазами враждебного ревьюера, ничего не запуская. Этот — проверяет, что код
собирается и работает на чистом окружении, но в его содержание не вникает.

Полезны оба и в этом порядке: сначала `check-before-commit` (окружение), потом
`pre-mr` (смысл). Обратный порядок означает, что ревью читает код, который может
даже не собираться.

## Точки подстановки

| Шаг | Сейчас (OrderShop) | Чем заменить |
| --- | --- | --- |
| 1–2 | `db:migrate:reset`, `db:seed` | Своими командами сброса схемы и загрузки данных |
| 3 | `npm run build -- --force` | Своей сборкой; флаг отключения кеша обязателен |
| 4–6 | `.scripts/dev-daemon.sh` | Штатным способом запуска стенда; 30 секунд подобрать по факту |
| 7 | `tests/run-collections.js` | Своим прогонщиком интеграционных тестов, либо убрать шаг |
| 8–9 | `npm test`, `npm run lint` | Своими командами |
| 12 | `<BASE_BRANCH>` | Своей целевой веткой (`main`, `develop`, `trunk`) |
| 13 | `.swap/mr-description/` | Своим каталогом для файлов вне гита |

**Если какого-то шага у тебя нет** — удали его, а не оставляй с чужой командой.
Шаг, который молча ничего не делает, хуже отсутствующего: он создаёт впечатление,
что проверка выполнена.
