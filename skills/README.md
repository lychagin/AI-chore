# Скиллы

Скиллы закрывают рабочие циклы, а не отдельные действия: не «получить комментарии», а
«пройти путь от чужой ремарки до ответа в MR». Бери их по одному — каждый требует
подстройки под свой трекер, свой хостинг репозитория и свой порядок работы в команде.

Конкретика в текстах — [проект-пример OrderShop](../examples/example-project.md).

---

## Что есть

| Скилл | Закрывает | Зависит от |
| --- | --- | --- |
| [`pre-mr`](pre-mr/SKILL.md) | Враждебное ревью ветки до того, как её увидит человек: субагенту дают только diff и постановку, он ищет проглоченные исключения, полуприменённые фиксы, пустые guard'ы; плюс мутационная проверка новых тестов, скан на секреты, живая верификация | — |
| [`commit`](commit/SKILL.md) | Коммит по Conventional Commits с проверкой формата до, а не после CI | — |
| [`get-comment`](get-comment/SKILL.md) | Выгрузка ремарок MR в файл, сгруппированный по критичности; файл хранит `discussion_id`, поэтому годится для последующих ответов | MCP-сервер `gitlab` |
| [`resolve-remarks`](resolve-remarks/SKILL.md) | Полный цикл: получить ремарки → категоризовать → исправить очевидные → обсудить спорные → закоммитить → ответить в MR | `get-comment` |
| [`reply-comment`](reply-comment/SKILL.md) | Только ответы: разобрать, что реально исправлено в коде, обновить файл ремарок и опубликовать ответы | `get-comment` |
| [`mine-patterns`](mine-patterns/SKILL.md) | Синтез правил ревью из накопленных комментариев MR: CLI-препроцессор, затем два прохода анализа → `review-patterns.json` и `.md` | [`tools/review-collector`](../tools/) |
| [`review-commits`](review-commits/SKILL.md) | Проверка своих коммитов по этой базе паттернов до push — показывает только нарушения | `mine-patterns` |
| [`handoff`](handoff/SKILL.md) | Файл передачи состояния для новой сессии: ветка, сделанное с SHA, остаток чек-листом, отвергнутые гипотезы, команды пересборки | — |
| [`check-before-commit`](check-before-commit/SKILL.md) | Полный цикл на чистом окружении: сброс данных, сборка без кеша, стенд, тесты, линт, описание MR | — |
| [`read-bug`](read-bug/SKILL.md) | Чтение бага из трекера: описание, скриншоты, комментарии коллег; синтез вероятной причины, вопросы при нехватке данных | MCP-сервер `openproject` |
| [`bugfix`](bugfix/SKILL.md) | Оркестратор полного цикла: тикет → классификация слоя по коду → выбор среды проверки → TDD → живая верификация → MR | `read-bug`, `pre-mr`, `/mr` |
| [`review-bug`](review-bug/SKILL.md) | Ревью бага с привязанным MR: чинит ли фикс реальную причину, обоснован ли, применены ли ремарки | `read-bug`, `get-comment` |
| [`nightly-triage`](nightly-triage/SKILL.md) | Разбор красного ночного прогона: три внешние причины первыми, чтение артефактов, классификация, воспроизведение | [`tools/nightly`](../tools/nightly/README.md) |

## Как они складываются

```
   баг в трекере                     ремарки пришли          свои коммиты
        │                                 │                       │
   read-bug → bugfix ────┐          get-comment ──┬── resolve-remarks
        │                │                        └── reply-comment
   review-bug ───────────┤                                        │
                         │      review-collector ── mine-patterns ── review-commits
   работа закончена      │           (утилита)      (база правил)  (проверка до push)
        │                │
   check-before-commit ──┴──→ pre-mr ──→ push/MR

   ночь покраснела                  сессия кончается
        │                                  │
   nightly-triage                       handoff
```

Два скилла на одну задачу с разных сторон: `check-before-commit` проверяет, что код
собирается и работает на чистом окружении, `pre-mr` — что он делает то, что заявлено.
Полезны оба и в этом порядке.

## Как приспособить к своему проекту

1. **Хостинг репозитория.** `get-comment`, `resolve-remarks`, `reply-comment` написаны
   под модель дискуссий GitLab: у ремарки есть `discussion_id`, тред резолвится
   отдельным вызовом. В GitHub PR модель другая (review comments привязаны к review) —
   меняется способ получения и ответа, но не порядок шагов.
2. **Трекер.** В текстах он назван нейтрально; там, где нужен номер задачи, подставь
   свой формат идентификатора вместо `TASK-1042`.
3. **Живая верификация в `pre-mr`.** Список сред («локально / тестовый стенд /
   nightly-стек») надо заменить на свои. Само правило менять не стоит: скилл требует
   явно записать, где проверяли, а если не проверяли — то почему. Пустая графа не
   допускается, и это главное, ради чего он существует.
4. **`mine-patterns` и `review-commits`** бесполезны на пустой истории: им нужен
   накопленный корпус комментариев к MR. На новом проекте отложи их на потом.
5. **Стенд.** `bugfix` и `review-bug` опираются на общий тестовый стенд. У `review-bug`
   для этого есть таблица «Требования к стенду»: четыре возможности и на каком шаге
   каждая нужна. Впиши туда свои команды один раз — без этого половина процедуры
   не выполняется.
6. **Таблица слоёв в `bugfix`.** Она отвечает на вопрос «где чинить» и ценна ровно
   настолько, насколько точно описывает твою архитектуру. Заполняй по мере разбора
   реальных багов, а не заранее.
7. **Ночной прогон.** `nightly-triage` написан под GitLab CI. Три внешние причины из
   Фазы 0 (данные загружены после старта сервисов, чужой код в образе, фильтр из
   расписания) встречаются почти в любом ночном пайплайне — их стоит оставить.

## Порядок внедрения

Скиллы независимы, но осмысленный порядок такой:

1. `commit`, `check-before-commit` — дёшево, эффект сразу.
2. `get-comment` → `resolve-remarks` / `reply-comment` — работа с ревью.
3. `pre-mr` — самостоятельная ценность, настройки почти не требует.
4. `read-bug` → `bugfix` → `review-bug` — цикл багфикса; нужен настроенный трекер.
5. `nightly-triage` — когда есть ночной прогон и он начал краснеть.
6. `mine-patterns`, `review-commits` — когда накопится история ревью.

## Чего здесь не будет

Двух скиллов исходного проекта — разбора переписки с заказчиком и переноса правок
макетов в требования. Оба держались на системе управления требованиями, которая
в этот репозиторий не переносится. Решение окончательное.
