# Resolve MR Remarks

Полный цикл работы с ремарками code review: анализ → категоризация → исправление → коммит → ответы в MR.

## Использование

```
/resolve-remarks <mr_number>
```

Например: `/resolve-remarks 1952`

---

## Фаза 1: Получить и категоризовать ремарки

### Шаг 1: Получить ремарки из MR

Вызвать `mcp__gitlab__get_mr_comments` с `mr_iid=<mr_number>` и `verbose=true`.

Игнорировать системные события (assigned, merge train, pipeline, approved).

### Шаг 1.5: Разведка роем (при 5+ ремарках)

Ремарки независимы друг от друга: каждая указывает на своё место в коде и проверяется
отдельно. При пяти и более — раздать по агенту на ремарку, модель `sonnet`.
При меньшем числе разбирать самому: накладные расходы не окупятся.

Агент работает **только на чтение** — правило из `critical-rules.md` («субагенты — на
разведку, не на правки») в силе, в промпте повторяется явно. Правки применяет основной
поток на Шаге 4.

Что даётся агенту на вход: текст ремарки, файл и строка из дискуссии, ссылка на
`critical-rules.md` и на релевантный паттерн из `memory_bank/patterns/`.

Формат ответа агента:

```
Ремарка:       <id дискуссии> — <краткая суть>
Место:         <file:line> — что там сейчас на самом деле
Утверждение:   подтверждается | не подтверждается | подтверждается частично
Категория:     ✅ очевидная | ⚠️ спорная | ❌ отклонить
Довод:         <почему именно эта категория, со ссылкой на правило или паттерн>
Правка:        <что конкретно изменить — текстом, без применения>
Риск:          <что ещё затрагивает эта правка, или «изолирована»>
```

Особое внимание к двум случаям, которые агент обязан отмечать явно:

- **ремарка уже неактуальна** — код изменился после её написания (частая причина ложного
  «исправлено»);
- **правка тянет за собой другие места** — тогда это не «очевидная», а спорная, независимо
  от того, как выглядит сама ремарка.

Основной поток проверяет ответы агентов и только после этого собирает категоризацию Шага 3.
Категория от агента — черновик, а не вердикт: вердикт остаётся за вами на Шаге 3.

### Шаг 2: Категоризовать каждую ремарку

Для каждой ремарки определить категорию и написать довод:

| Категория | Маркер | Критерии                                                                                                                                                    |
| --------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Очевидная | ✅     | Явная ошибка: неправильный HTTP статус, нарушение lint, опечатка, несоответствие паттерну проекта, отсутствующий example в OpenAPI, нарушение ESLint правил |
| Спорная   | ⚠️     | Архитектурное решение, субъективный выбор, неоднозначное требование, требует обсуждения                                                                     |
| Отклонить | ❌     | Код уже корректен, ремарка не применима, изменение выходит за scope задачи                                                                                  |

### Шаг 3: Показать пользователю категоризацию

Вывести список в формате:

```
📋 MR <number> — <N> ремарок

✅ Очевидные (N) — исправляем сразу:
  1. [файл:строка] Краткое описание
     Довод: почему очевидная

⚠️  Спорные (N) — нужно обсудить:
  1. [файл:строка] Краткое описание
     Довод: почему спорная

❌ Отклоняем (N) — финальное слово за тобой:
  1. [файл:строка] Краткое описание
     Довод: почему отклоняем
```

**Ждать подтверждения пользователя перед тем как продолжить.**

---

## Фаза 2: Исправить ремарки

### Шаг 4: Применить очевидные исправления

Для каждой ✅ ремарки:

1. Прочитать файл по указанному пути
2. Внести правку
3. После правки — проверить ESLint вывод (hook автоматически запустит lint)

Не коммитить после каждой правки — собираем всё в один коммит.

### Шаг 5: Обсудить спорные ремарки

Для каждой ⚠️ ремарки поочерёдно:

1. Показать текст ремарки и свою позицию
2. Ждать решения пользователя: исправить / отклонить
3. Если исправить — применить правку
4. Запомнить решение для ответа в MR

### Шаг 6: Показать отклонённые ремарки

Вывести список ❌ ремарок с доводами и ждать финального решения пользователя по каждой:

- Если пользователь передумал → перевести в ✅ и исправить
- Иначе → оставить отклонённой, ответить в MR с объяснением

---

## Фаза 3: Коммит

### Шаг 7: Создать коммит

После всех правок:

```bash
git add -A
git commit -m "fix(review): resolve MR #<number> remarks"
```

Если правок не было (все отклонены) — коммит не создавать.

---

## Фаза 4: Ответы в MR

### Шаг 8: Отправить ответы

Для каждой ремарки вызвать `mcp__gitlab__reply_to_discussion`:

**✅ Исправлено** (очевидная или спорная после обсуждения):

```
✅ Исправлено

[краткое объяснение что именно изменили — 1-3 предложения]
```

**❌ Отклонено** (по любой причине):

```
❌ Не вносим изменение

[объяснение почему — довод из категоризации или решение пользователя]
```

### Шаг 9: Resolve обсуждений

После отправки ответа вызвать `mcp__gitlab__resolve_mr_discussion` для всех ремарок где статус ✅ Исправлено.

Ремарки со статусом ❌ — НЕ резолвить (пусть reviewer решает сам).

---

## Шаг 10: Итоговый отчёт

Вывести сводку:

```
✅ Завершено — MR #<number>

Ремарок обработано: N
  ✅ Исправлено: N
  ❌ Отклонено: N

Коммит: <sha> (или "коммит не создан")
Ответов отправлено: N
Resolved: N
```

---

## MCP инструменты

- `mcp__gitlab__get_mr_comments` — получить ремарки
- `mcp__gitlab__reply_to_discussion` — отправить ответ
- `mcp__gitlab__resolve_mr_discussion` — отметить resolved
