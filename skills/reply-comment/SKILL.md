# Reply to MR Comments with Analysis

Анализирует исправления в коде по ремаркам review, обновляет файл с ремарками и отправляет ответы в MR.

## Использование

```
/reply-comment <mr_number>
```

Например: `/reply-comment 1702`

## Что делает

1. Находит последний файл с ремарками в каталоге `.swap/requirements/use_cases/review/` (тот же, что создаёт **get-comment**) по шаблону `mr-<mr_number>-remarks-*.md`
2. Для каждой ремарки:
   - Извлекает файл:строка из заголовка
   - Читает текущее состояние кода
   - Анализирует исправление относительно ремарки
   - Формирует вердикт (✅ исправлено / ⚠️ частично / ❌ не исправлено)
   - Обновляет файл с ремарками (добавляет секции **Анализ** и **Вердикт**)
3. Отправляет ответы в MR через MCP
4. Отмечает обсуждения как resolved если вердикт положительный

## Шаги выполнения

### Шаг 1: Найти файл с ремарками

```bash
ls -t .swap/requirements/use_cases/review/mr-<mr_number>-remarks-*.md | head -1
```

### Шаг 2: Парсинг ремарок

Для каждого замечания извлечь:

- `discussion_id` — из заголовка `[...]`
- `файл:строка` — из заголовка после discussion_id
- `Текст:` — о чём ремарка
- `Ответ:` — если уже заполнен

### Шаг 3: Анализ исправления

Для каждой ремарки с файлом:строкой:

1. **Читать файл** — использовать `Read` tool для указанной строки
2. **Сравнить с ремаркой** — проверка:
   - Изменён ли паттерн/значение/код?
   - Соответствует ли ожиданию из ремарки?
   - Есть ли побочные эффекты?
3. **Формировать вердикт:**

| Статус        | Маркер | Условие                               |
| ------------- | ------ | ------------------------------------- |
| Исправлено    | ✅     | Код соответствует требованиям ремарки |
| Частично      | ⚠️     | Частично исправлено, есть нюансы      |
| Не исправлено | ❌     | Проблема остаётся                     |
| Неприменимо   | 🔵     | Ремарка не требует исправления кода   |

### Шаг 4: Обновить файл с ремарками

Добавить под каждую ремарку:

```markdown
### [discussion_id] - файл:строка

**Автор:** @username
**Создан:** YYYY-MM-DD HH:MM

**Текст:**
🔴 **critical**: Паттерн `^[0-9]{10,15}$` не допускает знак `+`...

**Анализ:**

- Текущий код: `pattern: '^[0-9]{10,15}$'`
- Ожидается: `pattern: '^\\+?[0-9]{10,15}$'`
- Статус: код не изменён

**Вердикт:** ❌ Не исправлено

**Ответ:**

<!-- Сформулированный ответ для MR -->
```

### Шаг 5: Отправить ответы в MR

Для каждой ремарки с заполненным **Анализ** и **Вердикт**:

1. Сформулировать ответ на основе анализа
2. Вызвать `mcp__gitlab__reply_to_discussion`:
   - `mr_iid`: номер MR
   - `discussion_id`: из файла
   - `body`: текст ответа
3. Если вердикт ✅ → вызвать `mcp__gitlab__resolve_mr_discussion`

## Шаблон ответа для MR

### ✅ Исправлено

```
✅ Исправлено: [краткое описание что сделано]

Изменения:
- [конкретное изменение 1]
- [конкретное изменение 2]
```

### ⚠️ Частично

```
⚠️ Частично исправлено: [что сделано]

Осталось:
- [что ещё нужно сделать]
```

### ❌ Не исправлено

```
❌ Не исправлено: [причина]

Текущее состояние: [фактический код]
Ожидается: [что должно быть]
```

### 🔵 Неприменимо / Комментарий

```
📝 Комментарий: [объяснение]

[дополнительная информация если нужна]
```

## Особые случаи

### Ремарки без файла:строки

Для общих комментариев (без позиции в коде) — анализ не проводится, ответ формируется на основе текста ремарки.

### Несколько ремарок на одном файле

Группировать анализ по файлам для эффективности — читать файл один раз, обрабатывать все ремарки по нему.

### Файлы вне проекта

Если файл не найден — отметить вердикт как `⚠️ файл не найден` и продолжить.

## MCP инструменты

- `mcp__gitlab__reply_to_discussion` — отправить ответ
- `mcp__gitlab__resolve_mr_discussion` — отметить resolved
