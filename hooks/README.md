# Хуки

Здесь два разных типа файлов, и путать их не надо.

- **Исполняемые хуки** (`*.sh`) запускает сам Claude Code по событию, если они прописаны
  в `.claude/settings.json`. Работают всегда, независимо от того, что модель «решила».
- **Чек-листы** (`*.md`) не запускаются ничем. Это документы, которые агент читает
  проактивно на нужном этапе — их ценность в том, что правило записано и проверяемо.

Конкретика в текстах — [проект-пример OrderShop](../examples/example-project.md).

---

## Исполняемые хуки

| Файл | Событие | Что делает |
| --- | --- | --- |
| [`block-secret-dumps.sh`](block-secret-dumps.sh) | `PreToolUse(Bash)` | Блокирует команды, печатающие раскрытые секреты: `docker compose config` без `--no-interpolate`, голые `env`/`printenv`/`export -p`, вывод `.env`/`.envrc` целиком |
| [`format-edited-file.sh`](format-edited-file.sh) | `PostToolUse(Edit\|Write)` | Прогоняет prettier и `eslint --fix` по изменённому файлу, запускаясь из каталога с **ближайшим** конфигом, а не из корня |

Оба написаны так, чтобы **не мешать работе при собственной поломке**: если не удалось
разобрать вход или нет нужного интерпретатора — пропускают, а не блокируют. Для
`block-secret-dumps.sh` это осознанный размен: ложное срабатывание дороже пропуска.

Причина, по которой хук про секреты вообще появился, записана прямо в нём: субагент
выполнил `docker compose config` при проверке деплоя и выгрузил живой токен в
транскрипт — токен пришлось перевыпускать. Хук закрывает не гипотетический риск.

### Подключение

В `.claude/settings.json` целевого проекта:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/block-secret-dumps.sh" }]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/format-edited-file.sh" }]
      }
    ]
  }
}
```

Проверить, что бит выполнения на месте: `chmod +x .claude/hooks/*.sh`. Без него хук
молча игнорируется.

## Чек-листы

| Файл | Когда читать | Цель |
| --- | --- | --- |
| [`pre-task.md`](pre-task.md) | Перед началом новой задачи | Не начинать, не посмотрев на существующие паттерны и референсные примеры |
| [`pre-commit.md`](pre-commit.md) | Перед созданием коммита | Прогнать проверки, у которых заранее известен ожидаемый результат |

**Чек-листы не запускаются автоматически.** Чтобы они действительно применялись, на них
надо сослаться из `CLAUDE.md` проекта — иначе агент про них не вспомнит.

Обратная сторона: чек-лист, который врёт, хуже отсутствующего. Оба файла содержат
списки путей и команд под OrderShop; пока они не переписаны под твой проект, агент
пойдёт искать несуществующие файлы и решит, что проверка пройдена.

## Как приспособить к своему проекту

1. **`block-secret-dumps.sh`** переносится как есть. Дополни список правил под свои
   утечки: у каждого проекта свой набор команд, печатающих лишнее.
2. **`format-edited-file.sh`** предполагает prettier + eslint. Меняется на свой
   форматтер; логику «искать ближайший конфиг вверх по дереву» лучше сохранить — она
   и есть смысл хука.
3. **`pre-task.md`** — переписать списки паттернов и антипаттернов на свои. Хорошая
   отправная точка, если списка ещё нет: [`/mine-patterns`](../skills/mine-patterns/SKILL.md)
   синтезирует его из накопленных ремарок к MR.
4. **`pre-commit.md`** — переписать грепы. Сохрани форму «правило + команда + ожидаемый
   результат»: проверку «= пусто» агент трактует однозначно, а «убедись, что код
   хороший» — нет.

## Чего здесь нет

Третьего чек-листа, `on-error.md` (что читать, когда падают тесты или компиляция), —
он целиком состоял из разбора ошибок конкретной инфраструктуры исходного проекта, и
переносить там нечего. Если такой файл нужен, его форма проста: тип ошибки → куда
смотреть → какой паттерн проверить → какие команды прогнать.
