# Pre-Task Hook

**Триггер:** Перед началом работы над новой задачей
**Цель:** Убедиться что агент знаком с критичными правилами и паттернами проекта

---

## ✅ Обязательные действия

### 1. Прочитай критические уроки

**ОБЯЗАТЕЛЬНО прочитай:**

- `.claude/../../.docs/development/quick-reference.md` - Топ-10 правил + Quick Reference
  - 🔴 Критические правила (1-10): ВСЕГДА применять
  - 📚 Топ-10 правил разработки
  - 🚀 Quick Reference команды

**Почему важно:**

- Предотвращение повторения ошибок из прошлых code review
- ROI 7-10x: 1.5 ч чтения → экономия 10-15 ч исправлений
- Критические паттерны уже выучены на ошибках

### 2. Проверь чеклисты разработки

**Проверь соответствие задачи:**

- `.docs/development/code-review-guidelines.md` - Чек-лист перед разработкой

  Разделы чеклиста заводятся по слоям твоего проекта. На проекте-примере OrderShop:
  - Контракт API: Contract-First, переиспользуемые схемы, общий блок метаданных
  - Backend: типизированные ошибки, порядок параметров логгера, генерируемые валидаторы
  - Модель данных: составные ключи, генерация номеров, права
  - Архитектура: связи, резолверы, DRY

**Действия:**

- [ ] Определи компоненты, которые будут затронуты
- [ ] Проверь релевантные чеклисты для этих компонентов
- [ ] Найди референсные примеры в кодовой базе

### 3. Найди референсные примеры в Memory Bank

**Паттерны (если применимо к задаче).** Список ниже — с проекта-примера OrderShop;
замени его перечнем своих файлов из `memory_bank/patterns/`. Форма важнее содержания:
путь к файлу плюс полстроки о том, какой вопрос он закрывает.

**Контракт API:**

- `patterns/openapi-shared-schemas-reuse.md` - переиспользование схем вместо копипасты
- `patterns/openapi-entity-references.md` - как ссылаться на другую сущность

**Backend:**

- `patterns/backend-typed-errors.md` - типизированные клиентские и серверные ошибки
- `patterns/backend-generated-validators.md` - валидация из контракта, не руками
- `patterns/backend-logger-api.md` - правильный порядок параметров логгера

**Модель данных:**

- `patterns/data-model-dictionaries.md` - именование, единый файл словарей
- `patterns/data-model-links.md` - когда связь, а когда вложенный объект

**Anti-Patterns (НИКОГДА не делай):**

- `anti-patterns/direct-edges.md` - прямые связи вместо косвенных
- `anti-patterns/generic-entity-extension.md` - доменная логика в базовом типе

### 4. Используй Quick Reference команды

Команды ниже — под раскладку OrderShop (`src/`, `openapi/`, `data-model/`).
Перепиши пути под свой репозиторий; смысл каждой проверки сохраняется.

**Перед созданием словаря:**

```bash
rg "name: [a-z]" data-model/dictionaries.yaml
# Смотрим уже принятое именование и не изобретаем своё
```

**Перед созданием схем API:**

```bash
# Найти референсный пример схемы
fd "OrderRequestBody.yaml" openapi/

# Проверить, как ссылаются на сущности
rg "EntityRef" openapi/components/schemas/ -l

# Проверить, где переиспользуется общий блок метаданных
rg "EntityMetaInfo.yaml" openapi/components/schemas/ -l
```

**Проверка существующих паттернов:**

```bash
# Найти все сервисы
fd "\.service\.ts$" src/

# Найти логику прав
rg "hasPermission|checkPermission" src/ -t ts

# Поиск по спецификациям API
rg "EntityMetaInfo" openapi/ -t yaml
```

## 🎯 Workflow начала задачи

1. **Прочитай** `.claude/../../.docs/development/quick-reference.md` (3-5 мин)
   - Критические правила (1-10)
   - Топ-10 правил разработки
   - Quick Reference для твоей задачи

2. **Проверь** `.docs/development/code-review-guidelines.md` (2-3 мин)
   - Чек-лист перед разработкой
   - Определи релевантные секции

3. **Найди** референсные примеры (5-10 мин)
   - Паттерны в Memory Bank
   - Похожие сущности/сервисы в кодовой базе
   - Существующие OpenAPI schemas

4. **Составь** план с ссылками на примеры
   - Какие паттерны применимы
   - Какие файлы нужно создать/изменить
   - Проверочные команды для каждого шага

## ⚠️ Критические проверки перед началом

- [ ] **Contract-First**: спецификация API создана ДО кода?
- [ ] **Референсные примеры**: нашёл похожие сущности/сервисы?
- [ ] **Именование**: соблюдены конвенции проекта для словарей и схем?
- [ ] **Общие схемы**: переиспользую готовую вместо дублирования?
- [ ] **Ключи**: в составном ключе только скалярные поля, без массивов?
- [ ] **Права**: не создаю руками то, что генерируется?
