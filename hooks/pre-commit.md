# Pre-Commit Hook

**Триггер:** Перед созданием коммита
**Цель:** Убедиться, что код соответствует критичным паттернам проекта

> **Это шаблон.** Ценность файла — в форме, а не в конкретных командах: каждое правило
> сопровождается грепом, у которого заранее известен ожидаемый результат («пусто» или
> «только вот эти файлы»). Такую проверку агент выполняет и трактует однозначно, в
> отличие от формулировки «убедись, что код хороший».
>
> Все команды ниже написаны под [проект-пример OrderShop](../examples/example-project.md)
> и его раскладку (`src/`, `openapi/`, `data-model/`). Перепиши их под свой стек: список
> правил у каждого проекта свой и рождается из ремарок код-ревью, а не из этого файла.
> Хорошая отправная точка — [/mine-patterns](../skills/mine-patterns/SKILL.md), который
> синтезирует правила из накопленных комментариев к MR.

## ✅ Обязательные проверки

### 1. Запусти проверочные команды

**Build & Lint:**

```bash
npm run build
npm run lint
```

**Проверки контракта API:**

```bash
# Дублирование метаинформации вместо общей схемы (должно быть пусто!)
rg "createdAt:|updatedAt:|deletedAt:" openapi/components/schemas/ -l

# Где переиспользуется общий блок метаданных
rg "EntityMetaInfo.yaml" openapi/components/schemas/ -l

# POST-эндпоинты с кодом 201 без Location (по конвенции проекта должен быть 200)
rg "'201':" openapi/paths/ -A 2 -B 5 | grep -E "(post:|'201':|description:)"
```

**Проверки backend:**

```bash
# Голый Error вместо типизированной ошибки проекта (должно быть пусто!)
rg "throw new Error\(" src/ -n | grep -v "test/"

# Неправильный порядок аргументов логгера: (message, object) вместо (object, message)
rg 'this\.logger\.(info|warn|error)\("[^"]*",\s*\{' src/ -n

# parseInt вместо Number.parseInt
rg "parseInt\(" src/ -n | grep -v "Number.parseInt"

# Захардкоженные имена сервисов вместо констант
rg 'name:\s*"[a-z-]+"' src/ -A 1 -B 1 | grep -v "ServiceNames"
```

**Проверки модели данных:**

```bash
# Составные ключи с потенциальными массивами
rg "compositePK:" data-model/ -A 5

# Сущности с номерами должны иметь генератор последовательности
rg "field.name: number$" data-model/ -A 10 | grep "numberSequence"

# Руками написанные файлы прав там, где права генерируются (должно быть пусто!)
fd "Permissions-[a-z]+\.yaml" data-model/generated/
```

---

### 2. Убедись, что следуешь критичным паттернам

**Проверь вручную:**

#### Контракт API

- [ ] **Общая схема метаданных** переиспользуется (НЕ дублируй createdAt/updatedAt)
- [ ] **Ссылка на сущность** в теле запроса — через общий тип, а не инлайн-объект
- [ ] **Все простые типы** имеют `example` с реалистичным значением
- [ ] **Коды ответов** соответствуют конвенции проекта
- [ ] **Композиция схем** (`allOf`) там, где есть общая часть

#### Backend

- [ ] **Типизированные ошибки** с указанием кода причины (НЕ голый `Error`)
  - 400-499 → клиентская ошибка
  - 500-599 → серверная ошибка
- [ ] **Логгер**: `logger.info({ object }, "message")`, а не наоборот
- [ ] **Генерируемые валидаторы** из контракта, НЕ ручная валидация в обработчике
- [ ] **Константы** вместо строковых литералов для имён сервисов и событий
- [ ] **Number.parseInt** вместо глобального `parseInt`

#### Модель данных

- [ ] **Составной ключ**: ТОЛЬКО скалярные поля, без массивов
- [ ] **Генерация номеров**: у сущностей с номером есть целочисленное поле для фильтра
- [ ] **Права**: нет руками написанных файлов там, где они генерируются
- [ ] **Именование**: словари в едином регистре (`deliverySlot`, НЕ `delivery_slot`)

---

### 3. Проверь отсутствие дублирования кода

```bash
# Дублирование общей метаинформации (должно быть пусто!)
rg "createdAt:" openapi/components/schemas/ -A 5 | grep -v "EntityMetaInfo.yaml"

# Дублирование составных типов (адрес, деньги, период)
rg "fullAddress:" openapi/components/schemas/ -A 3

# Разросшиеся DTO — кандидаты на вынос общей части
fd "get\..*\.dto\.ts$" src/dto/ -x wc -l
```

## 📋 Полный чек-лист

### Build & Tests

- [ ] `npm run lint` — без ошибок
- [ ] `npm run build` — компилируется
- [ ] Все скрипты в `package.json` существуют

### Контракт API

- [ ] Спецификация соответствует макетам (`maxLength`, `minLength`)
- [ ] Используются общие схемы, а не копии
- [ ] Нет дублирования метаинформации: `rg "createdAt:|updatedAt:" schemas/ -l` = пусто
- [ ] Права на вложенные поля согласованы со схемами
- [ ] Все `example` заполнены реалистичными значениями

### Код

- [ ] Типизированные ошибки: `rg "throw new Error\(" src/ -n | grep -v "test/"` = пусто
- [ ] Логгер: `rg 'logger\.(info|error)\("[^"]*",\s*\{' src/ -n` = пусто
- [ ] Валидаторы: ручная валидация только для внутренних вызовов
- [ ] Нет захардкоженных имён сервисов
- [ ] `rg "parseInt\(" src/ | grep -v "Number.parseInt"` = пусто

### Модель данных

- [ ] Составной ключ — только скалярные поля
- [ ] У сущностей с номером есть целочисленное поле
- [ ] Нет руками написанных генерируемых файлов прав

### Testing & Docs

- [ ] Интеграционные тесты на граничные случаи
- [ ] Документация маппинга (если добавлялись фильтры)
- [ ] НЕТ отладочных логов
- [ ] План обновлён (если есть)

## 🚨 Типичные ошибки

Раздел ведётся по факту: сюда попадает то, что уже ловили на ревью дважды.
Ниже — примеры формы записи на OrderShop.

### 1. Дублирование общей метаинформации

```bash
# Должно вернуть ПУСТО
rg "createdAt:\s*$" openapi/components/schemas/ -l
```

Если не пусто → замени на `$ref: EntityMetaInfo.yaml`.

### 2. Ошибка без кода причины

```typescript
// ❌ НЕПРАВИЛЬНО — по тексту сообщения нельзя отличить причину
throw new ClientError("Error", 404, { ... });

// ✅ ПРАВИЛЬНО
throw new ClientError("Error", 404, { ... }, "ORDER_NOT_FOUND");
```

### 3. Неправильный порядок аргументов логгера

```typescript
// ❌ НЕПРАВИЛЬНО — объект не попадёт в структурированный лог
this.logger.info("Message", { data });

// ✅ ПРАВИЛЬНО
this.logger.info({ data }, "Message");
```

### 4. Составной ключ с массивом

```yaml
# ❌ НЕПРАВИЛЬНО
compositePK:
  - name
  - items # массив!

# ✅ ПРАВИЛЬНО — отдельное уникальное поле
fields:
  - field.name: orderCode
    field.attributes: [unique]
```
