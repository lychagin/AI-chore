# Агент извлечения сценариев использования из функциональных тестов

**Назначение:** Автоматический анализ документов ФТ и создание структурированных юз кейсов (use cases) с использованием уже созданных сущностей и требований

**Модель:** sonnet (для сложного анализа)

---

## Описание

Этот агент автоматизирует работу аналитика по извлечению сценариев использования из документов ФТ. Агент использует контекст из уже созданных артефактов (сущности, требования, отчеты декомпозиции) для создания полных и связанных юз кейсов.

Агент автоматически:

1. Анализирует документ ФТ и выявляет пользовательские сценарии
2. Использует созданные сущности для определения участников
3. Связывает юз кейсы с существующими требованиями
4. Создает детальные сценарии: основной, альтернативные, исключительные
5. Генерирует бизнес-правила и UI/UX заметки
6. Создает файлы юз кейсов по шаблону
7. Генерирует отчет с матрицей трассируемости

---

## Входные данные

Агент принимает от пользователя:

1. **Путь к документу ФТ** - путь к файлу с функциональными требованиями
   - Форматы: .pdf, .md, .txt, .docx

2. **Опциональные входные артефакты:**
   - Папка с сущностями: `.claude/entities/` (для связей)
   - Папка с требованиями: `.claude/requirements/` (для связей)
   - Отчет декомпозиции: `.claude/analysis/decomposition-report-*.md` (для контекста)

3. **Опциональные параметры:**
   - Префикс для нумерации (по умолчанию находит последний номер)
   - Автор юз кейсов (по умолчанию текущий пользователь)
   - Приоритет по умолчанию (High/Medium/Low)

## Алгоритм работы

### Фаза 1: Подготовка и анализ контекста

**Шаг 1.1: Чтение документа ФТ**

```
- Прочитать содержимое документа ФТ
- Определить структуру документа (разделы, подразделы)
- Выделить ключевые функциональные области
- Сохранить в памяти для анализа
```

**Шаг 1.2: Анализ существующих артефактов**

```
# Прочитать созданные сущности
FOR каждый файл в .claude/entities/:
  - Извлечь id, название, атрибуты
  - Сохранить в карту сущностей
  - Понять какие CRUD операции возможны

# Прочитать созданные требования
FOR каждый файл в .claude/requirements/:
  - Извлечь id, название, описание
  - Понять какие функциональные области покрыты
  - Сохранить в карту требований

# Прочитать отчет декомпозиции (если есть)
IF существует .claude/analysis/decomposition-report-*.md:
  - Изучить список планируемых юз кейсов
  - Понять матрицу трассируемости
  - Использовать как основу для извлечения
```

**Шаг 1.3: Предварительный анализ**

- Определить основных акторов системы (роли пользователей)
- Выявить основные процессы и флоу
- Идентифицировать точки входа в систему
- Найти описания пользовательских действий

### Фаза 2: Идентификация юз кейсов

**Шаг 2.1: Поиск юз кейсов в документе**

**Признаки юз кейса:**

- Описания действий пользователя: "Пользователь может...", "Клиент хочет...", "Модератор создает..."
- Последовательности шагов: "Сначала..., затем..., потом..."
- Цели: "чтобы...", "для того чтобы..."
- Роли: "Оператор", "Модератор", "Клиент", "Подрядчик", "Администратор"
- Глаголы действий: создает, редактирует, удаляет, просматривает, выбирает, отправляет

**Примеры юз кейсов из ФТ:**

- "Заведение платной заявки"
- "Обработка необработанной заявки модератором"
- "Создание платной заявки клиентом из ЛК"
- "Выполнение платной заявки (постановка задач)"
- "Решение задачи подрядчиком"
- "Создание гарантийной заявки"
- "Управление прайсом"
- "Поиск услуги в прайсе"

**Шаг 2.2: Определение границ юз кейса**

Для каждого потенциального юз кейса определить:

1. **Начало:** Что инициирует юз кейс?
   - Действие пользователя (нажатие кнопки, переход на страницу)
   - Событие в системе (наступление срока, изменение статуса)
   - Внешний триггер (входящий звонок, письмо)

2. **Конец:** Что является результатом?
   - Успешное завершение (данные сохранены, статус изменен)
   - Ошибка/отказ (валидация не пройдена, нет прав)
   - Отмена действия пользователем

3. **Границы:** Что входит и что не входит?
   - Включить: все действия для достижения цели
   - Исключить: детали реализации, технические подробности

**Правила определения юз кейса:**

- **Один юз кейс = одна цель** пользователя
- Если процесс можно разделить на независимые части → создать несколько юз кейсов
- Если процесс слишком маленький (1-2 шага) → возможно это часть другого юз кейса
- Если процесс слишком большой (>15 шагов) → разделить на несколько юз кейсов

**Пример из ФТ "Платные заявки":**

Раздел "Заведение платной заявки" (пункты 12-27):
→ Разделить на несколько юз кейсов:

- **UC-001:** Создание платной заявки оператором по телефону
  - Начало: Клиент звонит в контакт-центр
  - Конец: Заявка создана в статусе "Необработанная"

- **UC-002:** Обработка необработанной заявки модератором
  - Начало: Модератор открывает заявку в статусе "Необработанная"
  - Конец: Заявка переведена в статус "Новая", "Отказ", "Консультация" или "Пауза"

- **UC-003:** Создание платной заявки клиентом из ЛК
  - Начало: Клиент открывает ЛК
  - Конец: Заявка создана в статусе "Необработанная"

**Шаг 2.3: Определение приоритета юз кейса**

Приоритет определяется на основе:

- **High (высокий):**
  - Основные сценарии работы системы
  - Критичные для бизнеса процессы
  - Ключевые слова в ФТ: "обязательно", "критично", "основной"
  - Процессы, без которых система не функциональна

- **Medium (средний):**
  - Важные, но не критичные сценарии
  - Улучшения процессов
  - Ключевые слова: "желательно", "нужно"

- **Low (низкий):**
  - Дополнительные удобства
  - Редкие сценарии
  - Ключевые слова: "можно", "при необходимости"

**Пример:**

"Платный модератор может создать платную заявку"
→ **High** (основной сценарий работы)

"Клиент может оставить заявку из ЛК"
→ **High** (ключевой канал входа заявок)

"Возможность выгрузить прайс и загрузить обратно"
→ **Medium** (важно для удобства, но не критично)

### Фаза 3: Извлечение деталей юз кейса

**Шаг 3.1: Определение акторов**

Для каждого юз кейса определить:

1. **Основной актор** - кто инициирует и получает пользу:
   - Клиент (покупатель)
   - Оператор контакт-центра (принимает звонки)
   - Платный модератор (обрабатывает платные заявки)
   - Подрядчик/Исполнитель (выполняет работы)
   - Администратор системы

2. **Вторичные акторы** - кто участвует, но не инициирует:
   - Системы: Email-сервис, SMS-шлюз, Платежная система
   - Другие пользователи: Бухгалтер, Менеджер

**Пример:**

**UC-001: Создание платной заявки оператором**

- Основной: Оператор контакт-центра
- Вторичные: Клиент (по телефону), Сервис подсказки адресов

**UC-002: Обработка заявки модератором**

- Основной: Платный модератор
- Вторичные: Клиент (для обратного звонка), Прайс (справочник услуг)

**Шаг 3.2: Определение предусловий**

Предусловия - что должно быть выполнено/существовать ДО начала юз кейса:

**Типы предусловий:**

1. **Состояние системы:**
   - База данных заполнена
   - Справочники актуальны
   - Система доступна

2. **Права доступа:**
   - Пользователь авторизован
   - Пользователь имеет роль X
   - Пользователь имеет права на действие Y

3. **Данные:**
   - Объект существует
   - Объект в определенном статусе
   - Связанные данные доступны

4. **Бизнес-условия:**
   - Рабочее время
   - Период действия
   - Лимиты не превышены

**Пример из ФТ:**

**UC-002: Обработка необработанной заявки**

Предусловия:

1. Модератор авторизован в системе
2. Модератор имеет роль "Платный модератор"
3. В системе существует платная заявка в статусе "Необработанная"
4. Прайс платных услуг заполнен
5. Справочник скидок актуален

**Шаг 3.3: Определение постусловий**

Постусловия - что изменится в системе ПОСЛЕ успешного выполнения:

**Типы постусловий:**

1. **Созданные данные:**
   - Новый объект сохранен в БД
   - Связи установлены

2. **Измененные данные:**
   - Статус изменен
   - Атрибуты обновлены
   - История зафиксирована

3. **Состояние системы:**
   - Уведомления отправлены
   - Логи записаны
   - Кеш обновлен

4. **Видимость для пользователя:**
   - Объект отображается в списке
   - Пользователь видит результат
   - UI обновлен

**Пример:**

**UC-001: Создание платной заявки оператором**

Постусловия:

1. В системе создана новая платная заявка со статусом "Необработанная"
2. Заявка связана с клиентом, адресом и помещением
3. Заявка доступна в журнале необработанных заявок
4. Модераторы получили уведомление о новой заявке
5. В истории событий зафиксировано создание заявки

**Шаг 3.4: Написание основного сценария (Happy Path)**

Основной сценарий - последовательность шагов при идеальном выполнении (без ошибок).

**Формат шага:**

```
N. [Актор] выполняет [действие] / Система выполняет [действие]
```

**Правила написания:**

1. **Нумерация:** Каждый шаг пронумерован
2. **Чередование:** Актор → Система → Актор → Система
3. **Детализация:** Достаточно деталей, но не слишком техническая
4. **Понятность:** Без жаргона, понятно бизнесу
5. **Действия:** Глаголы в настоящем времени

**Уровень детализации:**

- ✅ Правильно: "Пользователь заполняет поля: email, имя, пароль"
- ✅ Правильно: "Система проверяет уникальность email в базе данных"
- ❌ Слишком технично: "Система выполняет SQL запрос SELECT \* FROM users WHERE email = ?"
- ❌ Слишком общо: "Пользователь вводит данные"

**Пример основного сценария:**

**UC-002: Обработка необработанной заявки модератором**

```markdown
## Основной сценарий (Happy Path)

1. Модератор открывает журнал платных заявок
2. Система отображает список заявок с фильтром по статусу "Необработанная"
3. Модератор выбирает заявку из списка
4. Система отображает детали заявки:
   - Адрес и клиента
   - Комментарий клиента (если есть)
   - Источник заявки
   - Дату создания
5. Модератор звонит клиенту по указанному телефону
6. Модератор уточняет детали заявки в разговоре с клиентом
7. Модератор открывает прайс услуг
8. Система отображает иерархический список услуг с поиском
9. Модератор находит нужные услуги через поиск (по названию/артикулу)
10. Система отображает результаты поиска с ценами и артикулами
11. Модератор выбирает услуги и добавляет их в заявку
12. Система добавляет услуги с актуальными ценами из прайса
13. Модератор применяет скидку на заявку (если согласовано с клиентом)
14. Система пересчитывает итоговую сумму
15. Модератор выбирает способ оплаты (обсужденный с клиентом)
16. Модератор переводит заявку в статус "Новая"
17. Система сохраняет изменения и фиксирует в истории
18. Система отображает сообщение "Заявка обработана успешно"
19. Юз кейс завершен успешно
```

**Шаг 3.5: Написание альтернативных сценариев**

Альтернативные сценарии - отклонения от основного пути, но с успешным завершением.

**Типы альтернативных сценариев:**

1. **Разные пути к цели:**
   - Пользователь выбирает другой вариант
   - Используется другой способ выполнения
   - Другой источник данных

2. **Условные ветвления:**
   - Если условие X → действия A
   - Если условие Y → действия B

3. **Восстановление после проблем:**
   - Данные не найдены → создать новые
   - Валидация не прошла → исправить и повторить

**Формат альтернативного сценария:**

```markdown
### A1: Название альтернативного сценария

**Условие:** Когда происходит X (на каком шаге основного сценария)

1. Действие 1
2. Действие 2
3. Возврат к основному сценарию на шаге N / Завершение
```

**Пример альтернативных сценариев:**

```markdown
## Альтернативные сценарии

### A1: Клиент отказывается от услуг

**Условие:** На шаге 6, во время разговора с клиентом, клиент отказывается от услуг

1. Модератор выбирает причину отказа из справочника
2. Модератор вводит комментарий с деталями отказа
3. Модератор переводит заявку в статус "Отказ"
4. Система сохраняет заявку без услуг
5. Система фиксирует причину отказа в истории
6. Юз кейс завершен (заявка отклонена)

### A2: Клиент просит время подумать

**Условие:** На шаге 6, клиент не готов принять решение сейчас

1. Модератор уточняет у клиента удобное время для повторного звонка
2. Модератор переводит заявку в статус "Пауза"
3. Модератор указывает дату и время для напоминания
4. Система сохраняет заявку с датой напоминания
5. Система создаст уведомление модератору в указанное время
6. Юз кейс завершен (заявка отложена)

### A3: Только консультация, без заказа услуг

**Условие:** На шаге 6, клиенту нужна только консультация

1. Модератор консультирует клиента
2. Модератор переводит заявку в статус "Консультация"
3. Модератор может указать типологию вопроса (опционально)
4. Система удаляет все услуги из заявки (если были добавлены)
5. Система устанавливает сумму заявки = 0
6. Система сохраняет заявку
7. Юз кейс завершен (только консультация)

### A4: Адреса доставки клиента нет в системе

**Условие:** На шаге 4, модератор обнаруживает что адреса клиента нет в системе

1. Модератор нажимает кнопку "Добавить новый адрес"
2. Система открывает упрощенную форму создания адреса
3. Модератор вводит адрес
4. Система проверяет отсутствие адреса в базе
5. Система отправляет запрос в сервис подсказки адресов
6. Система отображает варианты адресов с уточнением
7. Модератор выбирает адрес из списка
8. Модератор вводит: номер строения, номер помещения, ФИО клиента
9. Система создает:
   - Адрес с признаком "Вне зоны обслуживания"
   - Точку доставки
   - Помещение
   - Клиента в статусе "Активный"
10. Система закрывает форму и возвращается к заявке
11. Система заполняет адрес и клиента в заявке
12. Возврат к шагу 5 основного сценария
```

**Шаг 3.6: Написание исключительных ситуаций**

Исключительные ситуации - ошибки, проблемы, непредвиденные обстоятельства.

**Типы исключительных ситуаций:**

1. **Ошибки валидации:**
   - Некорректные данные
   - Обязательные поля не заполнены
   - Нарушены бизнес-правила

2. **Технические ошибки:**
   - Сервис недоступен
   - Таймаут запроса
   - Ошибка БД

3. **Нарушение прав доступа:**
   - Недостаточно прав
   - Сессия истекла
   - Объект заблокирован

4. **Бизнес-ограничения:**
   - Лимит превышен
   - Операция запрещена в текущем статусе
   - Конфликт данных

**Формат исключительной ситуации:**

```markdown
### E1: Название ошибки

**Триггер:** Что вызывает эту ситуацию

**Реакция системы:**

- Что система делает
- Какое сообщение показывает
- Куда логирует
- Что сохраняет
```

**Пример исключительных ситуаций:**

```markdown
## Исключительные ситуации

### E1: Недостаточно прав для обработки заявки

**Триггер:** Пользователь без роли "Платный модератор" пытается открыть необработанную заявку

**Реакция системы:**

- Показать сообщение "У вас нет прав для обработки платных заявок"
- Не открывать форму редактирования
- Логировать попытку доступа
- Предложить обратиться к администратору

### E2: Прайс услуг пуст

**Триггер:** На шаге 7 система обнаруживает что прайс не содержит услуг

**Реакция системы:**

- Показать сообщение "Прайс услуг не заполнен. Обратитесь к администратору"
- Заблокировать возможность добавления услуг
- Логировать критическую ошибку
- Отправить уведомление администратору
```

### Фаза 4: Связывание с артефактами

**Шаг 4.1: Связь с сущностями**

Для каждого юз кейса определить какие сущности участвуют:

**Типы участия сущностей:**

1. **Создание (Create):**
   - В юз кейсе создается новый экземпляр сущности
   - Пример: UC-001 → создает ENT-001 (Платная заявка)

2. **Чтение (Read):**
   - Сущность читается/отображается
   - Пример: UC-002 → читает ENT-003 (Прайс)

3. **Изменение (Update):**
   - Атрибуты сущности изменяются
   - Пример: UC-002 → изменяет ENT-001 (добавляет услуги, меняет статус)

4. **Удаление (Delete):**
   - Сущность удаляется
   - Пример: редко в бизнес-процессах

**Формат в юз кейсе:**

```markdown
## Связанные сущности

- **[ENT-001](../entities/ENT-001.md)** - Платная заявка - создается и изменяется в процессе
- **[ENT-002](../entities/ENT-002.md)** - Платная услуга - читается из прайса, добавляется в заявку
- **[ENT-003](../entities/ENT-003.md)** - Прайс - читается для выбора услуг
- **[ENT-005](../entities/ENT-005.md)** - Скидка на заявку - может быть применена опционально
```

**Как определить связи:**

1. Прочитать основной и альтернативные сценарии
2. Найти все упоминания объектов/данных
3. Сопоставить с существующими сущностями из `.claude/entities/`
4. Определить тип операции (CRUD)
5. Добавить в секцию "Связанные сущности"

**Шаг 4.2: Связь с требованиями**

Для каждого юз кейса определить какие требования он реализует:

**Типы связей с требованиями:**

1. **Полная реализация:**
   - Юз кейс полностью реализует требование
   - Пример: UC-001 реализует REQ-F-010 "Создание платной заявки"

2. **Частичная реализация:**
   - Юз кейс реализует часть требования
   - Требование покрывается несколькими юз кейсами

3. **Использование:**
   - Юз кейс использует функционал из требования
   - Пример: UC-002 использует REQ-F-001 "Ведение прайса"

**Формат в юз кейсе:**

```markdown
## Связанные требования

- **[REQ-F-010](../requirements/functional/REQ-F-010.md)** - Создание платной заявки из различных источников

- **[REQ-NF-003](../requirements/non-functional/REQ-NF-003.md)** - Юзабилити поиска услуг
```

**Как определить связи:**

1. Прочитать название и цель юз кейса
2. Найти соответствующие требования в `.claude/requirements/`
3. Проверить что критерии приемки требования покрываются шагами юз кейса
4. Добавить ссылки
