# OrderShop — проект-пример

Все агенты, скиллы и документы в этом репозитории писались на реальном проекте, из
которого была вычищена его специфика. Пустота на месте вычищенного делает инструкции
нечитаемыми: агент понимает «проверь контракт API» гораздо хуже, чем «проверь, что
`openapi/paths/v1_orders.yaml` соответствует схеме». Поэтому вместо пустоты подставлен
один сквозной вымышленный проект — **OrderShop**.

> **OrderShop — это пример, а не требование.** Ни один артефакт не обязывает тебя
> использовать Fastify, PostgreSQL или GitLab. Везде, где встречается конкретика
> OrderShop, её надо заменить своей — таблица подстановки ниже.

---

## Что за проект

Сервис приёма и обработки заказов. Клиент оформляет заказ сам через личный кабинет
либо диктует оператору по телефону; менеджер обрабатывает заказ, добавляет позиции из
каталога, применяет скидку и передаёт в доставку.

**Домен:** заказы, клиенты, позиции каталога, адреса доставки, скидки, статусы заказа.

**Роли:** Клиент, Оператор контакт-центра, Менеджер (модератор) заказов,
Исполнитель доставки, Администратор.

## Чего в примере намеренно нет

Исходный проект был на микросервисном фреймворке и графовой БД. Часть его инструкций
опиралась на механику, которой в других стеках просто не существует: миксины сервисов,
обход графа на заданную глубину, обратные рёбра, порядок применения файлов сидера.

Такие места **не переводились на OrderShop** — переводить нечего, механики нет. Они
либо выброшены, либо заменены ближайшим по смыслу действием (миграция, репозиторий,
связь по внешнему ключу). Там, где выброшено что-то содержательное, стоит пометка
в README соответствующего каталога.

Вывод для тебя: если в твоём стеке есть механика, которой нет у OrderShop, — её надо
дописать самому. Ни один из этих артефактов не знает про твой проект больше, чем ты
в него положишь.
