# Список всех команд Claude

## 🤖 Автоматическая декомпозиция (AI-агент)

### `/decompose`

**Описание:** Автоматический анализ неструктурированных документов и создание артефактов

**⭐ КЛЮЧЕВАЯ КОМАНДА ⭐**

Вместо ручного создания каждого артефакта, загрузите документы (ФТ, переписки) и агент автоматически создаст сущности, юз кейсы и требования.

**Что делает агент:**

1. Анализирует ФТ и переписки
2. Извлекает сущности с атрибутами и связями
3. Создает юз кейсы с полными сценариями
4. Формулирует требования с критериями приемки
5. Проверяет существующие артефакты на конфликты
6. Создает/обновляет файлы по шаблонам
7. Генерирует отчет с рекомендациями

**Когда использовать:**

- В начале проекта с большим объемом документов
- После встреч с клиентом (новые письма)
- При обновлении ФТ от заказчика
- Вместо ручного создания 10+ артефактов

**Режимы работы:**

1. Полная декомпозиция (default) - анализ всего, проверка конфликтов
2. Только новые - создаёт новое, не проверяет существующее
3. Обновление существующих - дополняет то что есть
4. Dry run - показывает план без создания файлов

**Входные данные:**

- Папка с ФТ (функциональные требования)
- Папка с переписками (.msg, .md, email)

**Результат:**

- Файлы сущностей в `entities/`
- Файлы юз кейсов в `use-cases/`
- Файлы требований в `requirements/`
- Отчет декомпозиции в `analysis/`
- Матрица трассируемости

**Примеры:**

```
/decompose

Claude: Укажите папку с ФТ:
Вы: ./input/specs/

Claude: Папка с переписками:
Вы: ./input/emails/

Claude: [анализ...]
✅ Создано:
- 12 сущностей
- 18 юз кейсов
- 25 требований

⚠️ Найдено 2 конфликта (требуют вашего решения)
```

**Разрешение конфликтов:**

Агент автоматически обнаруживает если извлеченная сущность/требование похоже на существующее. Показывает diff и спрашивает что делать.

**Важно:**

- Агент - помощник, не замена аналитику
- Всегда проверяйте созданные артефакты
- Дорабатывайте критерии приемки
- Используйте /validate после декомпозиции

## Команды для создания артефактов вручную

### `/new-entity`

**Описание:** Создать новую сущность (ENT-XXX)

**Примеры использования:**

- Создать сущность "Пользователь"
- Создать сущность "Заказ"
- Создать сущность "Товар"

**Что спросит:**

- Название сущности
- Описание
- Атрибуты (название, тип, обязательность)
- Бизнес-правила

**Результат:**

- Файл в `entities/ENT-XXX.md`
- Автоматически сгенерированный ID
- Заполненный шаблон

---

### `/new-usecase`

**Описание:** Создать новый юз кейс (UC-XXX)

**Примеры использования:**

- Создать юз кейс "Регистрация пользователя"
- Создать юз кейс "Оформление заказа"
- Создать юз кейс "Поиск товаров"

**Что спросит:**

- Название юз кейса
- Главный актор
- Цель (что хочет сделать пользователь)
- Основные шаги
- Приоритет (High/Medium/Low)

**Результат:**

- Файл в `use-cases/UC-XXX.md`
- Основной сценарий
- Шаблон для альтернативных сценариев
- Связи с сущностями

---

### `/new-requirement`

**Описание:** Создать новое требование (REQ-F-XXX или REQ-NF-XXX)

**Примеры использования:**

- Создать функциональное требование
- Создать требование безопасности
- Создать требование производительности

**Что спросит:**

- Тип (функциональное/нефункциональное)
- Название
- Детальное описание
- Приоритет (Must/Should/Could/Won't Have)
- Источник требования

**Результат:**

- Файл в `requirements/functional/` или `requirements/non-functional/`
- Критерии приемки
- Связи с юз кейсами

---

## Команды для работы с артефактами

### `/trace`

**Описание:** Показать все связи для артефакта

**Примеры использования:**

```
/trace ENT-001
/trace UC-005
/trace REQ-F-010
```

**Что покажет:**

- Прямые связи (на что ссылается артефакт)
- Обратные связи (что ссылается на артефакт)
- Проблемы ("висячие" ссылки, односторонние связи)
- Визуальную карту связей

**Результат:**

- Полная картина использования артефакта
- Список проблем (если есть)

---

### `/update-entity`

**Описание:** Обновить сущность и все связанные документы

**Примеры использования:**

- Добавить атрибут в сущность
- Изменить бизнес-правило
- Переименовать атрибут

**Что делает:**

1. Находит ВСЕ места использования сущности
2. Показывает что будет изменено
3. Просит подтверждение
4. Обновляет сущность и все связанные документы
5. Увеличивает версию
6. Добавляет запись в историю изменений

**Важно:** Использует `/trace` внутри для поиска всех связей

---

### `/validate`

**Описание:** Проверить весь проект на ошибки

**Когда использовать:**

- Минимум раз в неделю
- После массовых изменений
- Перед созданием ТЗ
- При передаче проекта другому аналитику

**Что проверяет:**

- Структурные проблемы (правильность шаблонов, ID, обязательные поля)
- Проблемы со связями ("висячие" ссылки, односторонние связи)
- Контентные проблемы (пустые секции, orphan артефакты)
- Версионность (история изменений, корректность дат)

**Результат:**

- Отчет с категориями: Критические ошибки, Предупреждения, Рекомендации
- Статистика проекта
- Предложения автоматических исправлений

## Команды для документирования

### `/log-communication`

**Описание:** Задокументировать общение с клиентом

**Примеры использования:**

- После встречи с клиентом
- После email переписки
- После звонка со стейкхолдером

**Что спросит:**

- Дата и время
- Канал (Встреча, Email, Zoom, Звонок, etc.)
- Участники
- Тема обсуждения
- Вопросы и ответы
- Принятые решения

**Результат:**

- Файл в `communications/COM-YYYY-XXX.md`
- Структурированный документ
- Связи с артефактами
- Action items
- Таблица принятых решений

---

### `/changelog-entry`

**Описание:** Создать запись об изменениях

**Когда использовать:**

- После значительных изменений в требованиях
- При обновлении юз кейсов
- При изменении сущностей
- Перед передачей проекта команде разработки

**Что спросит:**

- Версия (например: 1.0.0, 1.1.0)
- Тип (Major/Minor/Patch)
- Причина изменений
- Что добавлено/изменено/удалено

**Результат:**

- Файл в `changelog/YYYY-MM-DD-vX.Y.Z.md`
- Подробное описание изменений
- Влияние на проект
- Обновленные версии в артефактах

---

## Команды для анализа и отчетов

### `/generate-spec`

**Описание:** Сгенерировать полное техническое задание

**Когда использовать:**

- Проект готов для передачи разработчикам
- Нужно показать полную картину клиенту
- Требуется документация для тендера

**Что создаст:**

- Полное ТЗ со всеми требованиями
- Все юз кейсы с подробным описанием
- Модель данных (все сущности)
- Матрицу трассируемости
- Глоссарий терминов
- Диаграммы связей (Mermaid)

**Результат:**

- Файл в `analysis/technical-specification-vX.Y.Z.md`
- Готовое ТЗ для разработчиков

---

### `/find-gaps`

**Описание:** Найти пробелы в требованиях и покрытии

**Когда использовать:**

- Перед финализацией ТЗ
- Для проверки полноты анализа
- При ревью проекта

**Что найдет:**

- Юз кейсы без требований
- Требования без юз кейсов
- Сущности без использования
- Отсутствующие CRUD операции
- Несогласованности
- Типичные пропуски (обработка ошибок, права доступа, etc.)

**Результат:**

- Отчет в `analysis/gaps-analysis-YYYY-MM-DD.md`
- Матрица покрытия CRUD операций
- Приоритизированный список пробелов
- Предложения по созданию недостающих артефактов

---

### `/generate-diagrams`

**Описание:** Генерировать диаграммы из сущностей и юз кейсов

**Когда использовать:**

- Нужна визуализация модели данных
- Презентация функциональности клиенту
- Документация архитектуры
- Onboarding новых членов команды

**Что спросит:**

- Какие диаграммы создать:
  - ER-диаграмма (связи сущностей)
  - Use Case диаграмма (акторы и юз кейсы)
  - Диаграмма последовательности (для юз кейса)
  - Диаграмма классов (структура сущностей)
  - Все диаграммы

**Что создаст:**

- Диаграммы в формате Mermaid
- Файлы в `analysis/diagrams/`
- Легенды и описания
- README с индексом диаграмм

**Результат:**

- Визуальные диаграммы (рендерятся в GitHub)
- Готовы для включения в документацию
- Автоматически генерируются из реальных артефактов

**Примеры:**

```
/generate-diagrams

Claude: Какие диаграммы создать?
1. ER-диаграмма
2. Use Case диаграмма
3. Диаграммы последовательности
4. Все диаграммы

Вы: Все
```

---

### `/generate-tests`

**Описание:** Генерировать тестовые сценарии из юз кейсов

**Когда использовать:**

- Передача проекта QA команде
- Подготовка к тестированию
- Документирование приемочных тестов
- Автоматизация тестирования

**Что спросит:**

- Для какого юз кейса (UC-XXX или "все")
- Формат тестов:
  - BDD (Gherkin) - для автоматизации
  - Test Cases - для ручного тестирования
  - Checklist - быстрая проверка
  - Все форматы

**Что создаст:**

- Тестовые сценарии на основе юз кейсов
- Покрытие всех сценариев (основной + альтернативные + исключения)
- Граничные значения
- Тестовые данные
- Матрицу покрытия

**Результат:**

- Файлы в `analysis/test-scenarios/`
- BDD сценарии (.feature)
- Test cases (.md)
- Чек-листы
- Готовые тесты для QA

**Примеры:**

```
/generate-tests UC-001

Claude: Какой формат?
1. BDD (Gherkin)
2. Test Cases
3. Checklist
4. Все форматы

Вы: Все форматы

Claude: Создано:
- 15 BDD сценариев
- 13 test cases
- 1 чек-лист
Покрытие: 100%
```

## Комбинирование команд

### Типичные цепочки команд

**Создание нового функционала:**

```
1. /new-entity (создать сущности)
2. /new-usecase (создать юз кейсы)
3. /new-requirement (создать требования)
4. /trace ENT-XXX (проверить связи)
5. /validate (проверить консистентность)
```

**Обновление существующего:**

```
1. /log-communication (задокументировать обсуждение)
2. /update-entity (обновить сущность)
3. /validate (проверить что ничего не сломалось)
4. /changelog-entry (создать changelog)
```

**Финализация проекта:**

```
1. /validate (убедиться что нет ошибок)
2. /find-gaps (найти пробелы)
3. (исправить найденное)
4. /generate-diagrams (создать визуализацию)
5. /generate-tests (создать тестовые сценарии)
6. /generate-spec (создать ТЗ)
7. /changelog-entry (финальный changelog)
```

---

## Советы по использованию

1. **Всегда начинайте с `/new-entity`** - определите сущности до юз кейсов
2. **Регулярно используйте `/validate`** - не накапливайте ошибки
3. **Документируйте все встречи** - `/log-communication` после каждого общения
4. **Проверяйте связи** - `/trace` перед большими изменениями
5. **Используйте `/find-gaps`** - перед финализацией проекта
