# Утилиты

Самостоятельные программы, а не артефакты Claude Code. `install.sh` их **не**
раскладывает: у каждой свой способ подключения — `npm install`, регистрация
MCP-сервера, бит выполнения. Порядок описан в README внутри каждой.

Зависимости (`node_modules`, `.venv`, `dist`, `__pycache__`, файлы блокировки)
в репозиторий не кладутся — ставятся на месте.

## С чего начать

- **Работаешь с MR и ревью** → `mr-template` и `mcp-servers/mcp-gitlab`. Дают
  осмысленный эффект сразу, настройка — две переменные окружения.
- **Накопилась история ревью** → `review-collector`. На новом проекте бесполезен:
  анализ на десятке комментариев даёт шум, ощутимый результат — от нескольких сотен.
- **Нужен доступ к базе из агента** → `mcp-servers/mcp-dgraph-server`. Требует сборки.
- **Остальное** — по мере надобности, они не связаны друг с другом.

## Общее правило адаптации

Три утилиты (`mr-template`, `review-collector`, `mr-monitor`) и два MCP-сервера
написаны под связку GitLab + OpenProject. Во всех пяти привязка изолирована в один
файл HTTP-клиента: под другой хостинг или трекер переписывается он, а логика вокруг
переносится без изменений. Что именно править — в разделе «Как приспособить
к своему проекту» README каждой утилиты.

`eml-to-md`, `md2pdf` и `docker-tools` от проекта не зависят вовсе — в них меняются
только пути в примерах.

## Чего здесь нет

Утилиты, которые нельзя оторвать от исходного стека, не переносились. Самый крупный
такой случай — два десятка зондов для разбора зависаний ночного прогона: они смотрели
внутрь конкретной базы и конкретного транспорта, и после замены стека от них не
остаётся ничего рабочего. Переносимой оказалась методика, а не код — она описана
в [`nightly/README.md`](nightly/README.md).
