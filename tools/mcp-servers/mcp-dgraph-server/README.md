# MCP DGraph Server

MCP (Model Context Protocol) сервер для интеграции с DGraph базой данных.

## Интеграция с dev окружением

MCP сервер полностью интегрирован в dev окружение проекта и автоматически использует существующую конфигурацию DGraph.

### Быстрый запуск:

```bash
# Полная настройка dev окружения с MCP
npm run dc:dev_setup

# Или по шагам:
npm run dc:dev_up    # Запуск dev окружения + сборка MCP
npm run dc:dev_down  # Остановка dev окружения
```

### Управление MCP сервером:

```bash
npm run mcp:build    # Сборка MCP сервера
npm run mcp:status   # Проверка статуса
npm run mcp:start:bg # Подготовка к запуску (проверка сборки)
npm run mcp:stop     # Информация об остановке
```

## Конфигурация

MCP сервер автоматически использует файл конфигурации:
`infrastructure/configs/service/.env.development`

Основные настройки DGraph:

- `DGRAPH_CONNECT_URL=localhost:19080` - адрес DGraph Alpha
- `DGRAPH_ALPHA_ADDRESSES=localhost:19080` - адреса DGraph серверов
- `DGRAPH_DEBUG=false` - режим отладки

## Установка и сборка

MCP сервер автоматически собирается при запуске dev окружения:

```bash
npm run dc:dev_up  # Включает сборку MCP сервера
```

Для ручной сборки:

```bash
npm run mcp:build
```

## Запуск

MCP сервер запускается автоматически Cursor'ом при использовании MCP инструментов.

Для ручного запуска (для тестирования):

```bash
npm run mcp:start
```

## Интеграция с Cursor

Для интеграции с Cursor добавьте в конфигурацию MCP:

```json
{
  "mcpServers": {
    "dgraph": {
      "command": "node",
      "args": ["<путь к репозиторию>/tools/mcp-servers/mcp-dgraph-server/dist/index.js"],
      "env": {
        "DGRAPH_CONNECT_URL": "localhost:19080",
        "DGRAPH_DEBUG": "false"
      }
    }
  }
}
```

## Доступные инструменты

### dgraph_query

Выполняет GraphQL+ запрос к DGraph.

**Параметры:**

- `query` (string, обязательный) - GraphQL+ запрос
- `variables` (object, опциональный) - переменные для запроса

### dgraph_mutate

Выполняет мутацию в DGraph.

**Параметры:**

- `data` (object, обязательный) - данные для мутации

### dgraph_delete

Удаляет данные из DGraph.

**Параметры:**

- `deleteJson` (object, обязательный) - данные для удаления
- `setJson` (object, опциональный) - дополнительные данные

### dgraph_upsert

Выполняет upsert операцию в DGraph.

**Параметры:**

- `query` (string, обязательный) - запрос для поиска существующих данных
- `data` (object, обязательный) - данные для вставки/обновления
- `conditions` (string, опциональный) - дополнительные условия

### dgraph_alter_schema

Изменяет схему DGraph.

**Параметры:**

- `schema` (string, обязательный) - схема DGraph в формате DQL

### dgraph_get_stats

Получает статистику базы данных DGraph.

**Параметры:**

- `detailed` (boolean, опциональный) - получить детальную статистику

### dgraph_search

Поиск по тексту в DGraph с использованием full-text search.

**Параметры:**

- `searchTerm` (string, обязательный) - поисковый запрос
- `entityType` (string, опциональный) - тип сущности для поиска
- `limit` (number, опциональный) - максимальное количество результатов

### dgraph_export

Экспорт данных из DGraph в различных форматах.

**Параметры:**

- `query` (string, обязательный) - запрос для экспорта данных
- `format` (string, опциональный) - формат экспорта (json, csv, rdf)
- `filename` (string, опциональный) - имя файла для экспорта

### dgraph_health_check

Проверяет состояние здоровья DGraph базы данных.

**Параметры:**

- `timeout` (number, опциональный) - таймаут проверки в миллисекундах

### dgraph_get_schema

Получает текущую схему DGraph.

**Параметры:**

- `format` (string, опциональный) - формат схемы (dql, json, graphql)

### dgraph_backup

Создает резервную копию данных DGraph.

**Параметры:**

- `destination` (string, опциональный) - путь для сохранения резервной копии
- `includeSchema` (boolean, опциональный) - включить схему в резервную копию

### dgraph_analyze_data

Анализ данных в DGraph - поиск аномалий, дубликатов, связей.

**Параметры:**

- `entityType` (string, опциональный) - тип сущности для анализа
- `analysisType` (string, опциональный) - тип анализа (duplicates, anomalies, relationships, all)

### dgraph_upsert

Выполняет upsert операцию.

**Параметры:**

- `query` (string, обязательный) - запрос для поиска
- `data` (object, обязательный) - данные для вставки/обновления
- `conditions` (string, опциональный) - дополнительные условия

### dgraph_alter_schema

Изменяет схему DGraph.

**Параметры:**

- `schema` (string, обязательный) - схема в формате DQL

## Как работает MCP сервер

### Архитектура взаимодействия

MCP (Model Context Protocol) сервер выступает как **мост** между Cursor (AI ассистент) и DGraph базой данных:

```
Cursor (AI) ←→ MCP Сервер ←→ DGraph База данных
```

### Зачем нужен MCP сервер?

1. **Безопасность**: MCP сервер предоставляет контролируемый интерфейс к базе данных, ограничивая доступ только необходимыми операциями
2. **Абстракция**: Скрывает сложность GraphQL+ запросов от AI ассистента
3. **Валидация**: Проверяет корректность запросов перед отправкой в DGraph
4. **Логирование**: Может вести логи всех операций с базой данных
5. **Кэширование**: В будущем может кэшировать часто используемые запросы

### Как происходит взаимодействие

1. **Пользователь** задает вопрос в Cursor (например: "Сколько домов в базе?")
2. **Cursor** анализирует вопрос и определяет, что нужен доступ к DGraph
3. **Cursor** запускает MCP сервер (если не запущен) и отправляет запрос через MCP протокол
4. **MCP сервер** получает запрос, преобразует его в GraphQL+ и отправляет в DGraph
5. **DGraph** выполняет запрос и возвращает результат
6. **MCP сервер** форматирует ответ и отправляет обратно в Cursor
7. **Cursor** получает данные и формирует ответ пользователю

### Расширение функциональности

MCP сервер можно дополнять новыми методами в следующих случаях:

#### Когда добавлять новые инструменты:

- **Новые типы запросов**: Специфичные для бизнес-логики запросы
- **Агрегация данных**: Сложные аналитические запросы
- **Валидация**: Проверка данных перед сохранением
- **Трансформация**: Преобразование данных в удобный формат
- **Безопасность**: Дополнительные проверки прав доступа

#### Примеры расширений:

```typescript
// Новый инструмент для аналитики
{
  name: "dgraph_analytics",
  description: "Выполнить аналитический запрос",
  inputSchema: {
    type: "object",
    properties: {
      reportType: { type: "string" },
      filters: { type: "object" }
    }
  }
}

// Инструмент для валидации
{
  name: "dgraph_validate",
  description: "Проверить корректность данных",
  inputSchema: {
    type: "object",
    properties: {
      data: { type: "object" },
      schema: { type: "string" }
    }
  }
}
```

#### Где добавлять:

Новые инструменты добавляются в массив `tools` в файле `src/index.ts`:

```typescript
const tools: Tool[] = [
  // Существующие инструменты...
  {
    name: "your_new_tool",
    description: "Описание нового инструмента",
    inputSchema: {
      /* схема параметров */
    },
  },
];
```

### Преимущества MCP подхода

1. **Модульность**: Каждый инструмент выполняет одну конкретную задачу
2. **Переиспользование**: Инструменты можно использовать в разных контекстах
3. **Тестируемость**: Каждый инструмент можно тестировать отдельно
4. **Масштабируемость**: Легко добавлять новые возможности без изменения основной архитектуры
5. **Безопасность**: Контролируемый доступ к базе данных через предопределенные интерфейсы

## Как приспособить к своему проекту

### Клиент базы

Сервер обращается к базе через [`src/dgraph-client.ts`](src/dgraph-client.ts) — тонкую
обёртку над `dgraph-js`. В исходном проекте на её месте был общий компонент
монорепозитория; его нельзя утащить отдельно, поэтому воспроизведено ровно то, что
вызывает `index.ts`: конструктор, `query`, `mutate`, `delete`, `upsert`, `alterSchema`.

Чего в этой обёртке нет по сравнению с оригиналом:

- повторов при конфликте транзакции — `mutate` падает сразу;
- кэша метаданных;
- дедлайна на вызов — таймаут задаёт gRPC по умолчанию.

Если нужно иное поведение — замени файл своей реализацией, сохранив сигнатуры.
Для другой базы (не DGraph) заменяется он же: `index.ts` больше ничего о хранилище
не знает.

### Конфигурация

Порядок: переменные процесса → `.env` рядом с сервером → путь из `DGRAPH_MCP_ENV_FILE`.
Значения из окружения имеют приоритет. Шаблон — [`env.example`](env.example).

Адрес указывается на **gRPC-порт** alpha-ноды (обычно `9080`), а не на HTTP-порт
`8080`: попытка подключиться к HTTP даёт таймаут без внятной ошибки.

### Сборка

```bash
npm install --prefix tools/mcp-servers/mcp-dgraph-server
npm run build --prefix tools/mcp-servers/mcp-dgraph-server
```

Клиент запускает `dist/index.js`, поэтому без сборки сервер не поднимется.
